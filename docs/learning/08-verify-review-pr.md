# 08 検証・独立レビュー・PR・マージ: ゲートつきの出荷

## ねらい
「検証 → 独立レビュー → PR → CI → マージ」を、**AI の申告ではなく、記録と状態で確かめながら**進める仕組みを理解します。bash から `git push` や `gh pr merge` を禁止した代わりに、**専用のツール**を作った理由も扱います。

## 何を作ったか
| ファイル | 役割 |
|---|---|
| `flow/verify.ts`(62 行) | 検証コマンドの**検出**と、出力の要約(純粋関数) |
| `flow/review.ts`(57 行) | レビューの依頼文の組み立てと、**判定の読み取り**(純粋関数) |
| `flow/fingerprint.ts`(42 行) | 作業ツリーの**指紋**(純粋関数) |
| `flow/pr.ts`(200 行) | PR 本文の生成、CI の判定、**マージのゲート**、ブランチ保護のルールセット(純粋関数) |
| `flow/git-tools.ts`(397 行) | `harness_worktree` / `harness_ensure_protection` / `harness_pr_create` / `harness_pr_merge`(Pi への接続) |
| `flow/register.ts` | `harness_verify` / `harness_review` / `plan_report` |
| `agents/reviewer.md` | レビュー担当(読み取り専用) |

## 仕組み

### 1. 検証(`harness_verify`)
プロジェクトの検証コマンドを、次の**優先順位**で決めて実行します。
1. `.harness/verify.json` の `{ "commands": ["npm run check"] }`(明示)
2. `package.json` の `check` スクリプト
3. `lint` → `typecheck` → `test` → `build`(あるものだけ、この順)
4. **何もなければ**: 「**未検証**」として記録(完了にはできるが、完了報告に「未検証」と書かれ、**自動マージはしない**)

実行は、`ctx.executeTool("bash", ...)` で、**ガード([03](03-guards.md))を通して**行います(検証コマンドも、同じ検査を受ける)。結果は、**指紋つき**で、計画に記録されます。

### 2. 独立レビュー(`harness_review`)
- **新しい文脈**の、**読み取り専用**の `reviewer` サブエージェント([06](06-subagents.md))に、**差分と要件だけ**を渡す。**実装側の説明は、渡さない**
- レビュー担当は、最後の行に、`<approved/>` か `<disapproved/>` を書く
- **マーカーがない・エラー・中断は、承認ではない**(fail-closed)。両方あれば、却下
- 差分の中に書かれた指示(「承認せよ」など)は、データとして扱う(`reviewer.md`)
- 却下された場合は、差し戻しとして数える([07](07-plan-and-loop.md))。再レビューは、**直した差分だけ**が対象

### 3. 指紋(fingerprint)
```ts
// 追跡中 + 未追跡(無視されていない)のファイルを、パス順に並べ、
// 「パス + 内容の sha256」をまとめて sha256
```
検証・レビューの記録に、そのときの指紋を持たせ、完了・マージのときに、**いまの指紋と一致するか**を比べます。**1 文字でも変えれば、検証は無効**になります。

### 4. ブランチ保護(`harness_ensure_protection`)
**GitHub の側で、既定ブランチへの直接 push を禁止**します(ルールセット)。ハーネスの `git push` ガードが、万一破られても、**GitHub が止める**二重の壁です。
- ルール: 削除の禁止・force push の禁止・PR 必須・(あれば)必須のステータスチェック。**bypass の主体は置かない**(管理者も直接 push できない)
- すでに有効なルールセットがあるか確認し、**なければ、ユーザーの確認のうえ**作る
- `harness_pr_create` が、初回に、自動で呼ぶ

### 5. PR の作成(`harness_pr_create`)
1. 既定ブランチの上なら、**拒否**(作業ブランチを作れ)
2. コミットされていない変更があれば、**拒否**(細かくコミットしてから)
3. ブランチ保護を確認・設定
4. `git push -u origin <ブランチ>`(**ホスト側の処理**。bash の `git push` ではない)
5. PR を作る(すでにあれば更新)。本文は、**差分とコミットから**、「概要 / 変更点 / 確認方法」の**固定の形**で自動生成(確認方法には、検証の記録、または「未検証」)

### 6. マージ(`harness_pr_merge`)とゲート(`mergeBlockers`)
マージは、次の**すべて**を満たすときだけ通ります。
| 条件 | 理由 |
|---|---|
| メインセッションから | サブエージェントは、マージできない |
| **CI のチェックが、すべて成功** | 無し(`none`)・失敗・実行中は、すべて拒否。**未検証の変更は、自動でマージしない** |
| 確定した計画がある | 検証・レビューの記録がないと、確認できない |
| **直近の検証が、成功**し、指紋が一致 | 検証のあとに、変更がないこと |
| レビューが必要な項目があるなら、**承認**され、指紋が一致 | |
| 未着手・進行中の項目が 0 | |

### 7. worktree(`harness_worktree`)
並列に書き込むサブエージェントのために、**別々の作業ディレクトリ**を作ります(`<repo>.worktrees/<ブランチ名>`)。
- 作るのは、**作業ブランチだけ**(既定ブランチは拒否)
- **削除は、このハーネスが作ったものだけ**。未保存の変更があれば、残して報告(`--force` は使わない)

### 8. 完了報告(`plan_report`)
`flow/report.ts`。**要件ごとの完了・未完了と理由、検証・レビューの結果、作成・マージした PR、自分で判断したこと、ユーザーへの依頼**を、機械的に組み立てます。AI は、それを**そのまま**最終報告として書きます。

## なぜこう実装したか
| 選んだこと | 却下した案 | 理由 |
|---|---|---|
| **Git・GitHub の書き込みを、bash ではなく、専用ツールにした** | bash の `git push` を、許可リストで許す | bash は何でも書ける。**ツールなら、実行の前に、条件(検証・レビュー済みか、CI は通ったか)を、コードで確かめられる**。実行は、ホスト側で、固定の引数だけ |
| **独立レビューに、差分と要件だけを渡す** | 実装の経緯も、渡す | 経緯を渡すと、**実装した側の考えに、引きずられる**。「新しい目」で見るのが、独立レビューの価値 |
| **レビューは、読み取り専用** | 直させる | レビュー担当が、直してしまうと、何が直ったか分からず、**独立性も、崩れる**。直すのは、メイン |
| **判定は、マーカー。なければ、却下** | 文章から、承認かを推測 | 推測は、**間違える**。形式を決め、**守られなければ、承認ではない**側に倒す |
| **指紋で、「最後の変更のあと」を確かめる** | 「検証したよ」を信じる | 「検証してから、少しだけ直した」が、いちばん危ない。**直したら、無効**にする |
| **GitHub のブランチ保護を、必ず設定する** | ハーネスのガードだけ | ガードは、**自作で、穴があるかもしれない**。GitHub 側の保護は、**別の壁**。多層にする |
| **PR 本文を、自動で作る** | AI に、自由に書かせる | 毎回、同じ形で、**読みやすい**。「確認方法」に、検証の結果が、必ず入る |
| **検証コマンドがなければ、自動マージしない** | 通して良い | **確認できていない変更を、自動で、既定ブランチに入れない**。人間が見る |
| **worktree の削除を、自分が作ったものに限る** | 何でも削除 | 並行して動く、**他のセッションの作業を、壊さない** |
| **ルールの判定を、純粋関数にした** | `register.ts` に、直接書く | **マージのゲート**は、間違えると事故になる。Pi と GitHub なしで、網羅的にテストできる(`tests/pr.test.ts`) |

## Claude Code では
| 観点 | Claude Code | このハーネス |
|---|---|---|
| 検証の強制 | **`Stop` フック**で、「テストが通っていないなら、続けさせる」を書く。自分で書く必要がある(未確認:標準では、強制しない) | 完了のゲートに、組み込み(指紋つき) |
| 独立レビュー | **サブエージェント**(読み取り専用のツールだけ)に、レビューさせる。`/review` などの組み込みコマンド・スキルがある(未確認:細部) | `harness_review`(差分と要件だけを渡し、マーカーで判定) |
| PR・マージ | `gh` コマンドを、bash で実行。権限ルール(`Bash(gh pr merge *)` を `ask` / `deny` にする、など)で制御 | **bash では禁止**し、専用ツールで、条件つきで実行 |
| ブランチ保護 | Claude Code の機能ではない。**GitHub の設定** | `harness_ensure_protection` が、確認・作成 |
| 並列の作業ディレクトリ | **サブエージェントの `isolation: worktree`** など、組み込みの worktree の仕組み(公式ドキュメントの記載は、細部を未確認) | `harness_worktree`(自作) |
| 完了の報告 | 自由な文章 | `plan_report` で、機械的に組み立て |

**違いの要点:**
- Claude Code でも、同じことは、**フックと権限ルールを組み合わせて**実現できます。違いは、**どこまで、組み込みか**。このハーネスは、「検証 → レビュー → マージ」を、**1 つの流れとして、あらかじめ組んだ**ものです。
- 一番大きい違いは、**「完了」の根拠が、記録(指紋つき)で、機械的に確かめられる**こと。Claude Code で、同じ強さにするには、`Stop` フックのスクリプトを、自分で書く必要があります。
- 一方、Claude Code の標準機能(`/review` など)は、**メンテナンスされ、改善される**のに対し、このハーネスは、**自分で保守**します。

## 試してみよう
1. 小さなプロジェクト(`package.json` に、`"check": "echo ok"`)を作り、`harness_verify` を、AI に実行させる。`.harness/verify.json` で、コマンドを差し替えてみる。
2. 検証後に、ファイルを 1 文字変えて、`plan_update(done)` が、**「最後の検証のあとに、変更がありました」**で拒否されるのを確認する。
3. `tests/pr.test.ts` を読み、`mergeBlockers` の、**すべての拒否理由**を、表にする。
4. `harness_review` を、実際のモデルで試す(最初は、小さな差分で)。**`<approved/>` を、書き忘れたら、どうなるか**を、`tests/verify.test.ts` から、確認する。
5. 自分の GitHub のテスト用リポジトリで、`harness_ensure_protection` を試す(管理者の権限が必要)。**注意:** ルールセットが作られる。試したあとは、設定画面で確認し、不要なら削除する。
6. `harness_pr_create` で、PR を作る(テスト用のリポジトリで)。本文の「確認方法」に、何が入るかを見る。

## 限界と注意
- **実際の GitHub での、`harness_pr_create` / `harness_pr_merge` / ブランチ保護の動作は、未検証**です(純粋関数と、コマンドの組み立ては、テスト済み。実機は、これから)。
- **`harness_review` は、実際の LLM で未検証**。レビューの質は、モデルしだい。
- CI が、**まったくない**リポジトリでは、マージのゲートが、常に「CI のチェックがありません」で、止まる(意図した動作)。
- レビュー担当は、**読み取り専用でも、読んだ内容に影響されうる**(プロンプトインジェクション)。マーカーの規則と、メインの最終判断で、**緩和**している。
- ルールセットは、**GitHub の管理者の権限**が必要。権限がなければ、作れず、**警告**になる。
