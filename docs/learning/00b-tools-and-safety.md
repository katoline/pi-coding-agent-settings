## 1. 標準の 4 つのツールは、何ができるか

結論から: **ご理解のとおりです。** 細かい仕様を足します(実装を読んで確認)。

| ツール | できること | 細かい仕様 |
|---|---|---|
| `read` | ファイルの中身を読む。画像(jpg・png・gif・webp・bmp)も読める | **1 回で 2000 行、または 50 KB まで**。超えたら切って、「`offset=…` で続きを読め」と案内する。範囲は `offset`(開始行)と `limit`(行数)で指定 |
| `write` | ファイルを**新規作成**、または**丸ごと上書き** | 親のフォルダが無ければ、**自動で作る**。**上書きの確認はしない** |
| `edit` | **既存のファイル**の一部を、**文字列の置き換え**で修正する | `oldText`(置き換え前)は、**ファイルの中で 1 か所だけに一致**する必要がある(一致しなければ失敗)。1 回の呼び出しで、複数の場所を直せる。**ファイルを新規作成することはできない**(それは `write`) |
| `bash` | シェルのコマンドを実行し、標準出力・標準エラーを返す | **作業フォルダ(cwd)**で実行。**時間の既定の上限はない**(指定すれば、秒で制限できる)。出力は**最後の 2000 行 / 50 KB**に切られ、全文は一時ファイルに保存される |

### 「バッシュが使えるなら、`edit` や `write` もいらないのでは?」
動作上は、`bash` だけでも、ほぼ何でもできます(`cat`、`sed`、`echo > file`)。それでも専用のツールがあるのは、**私の推測**ですが、次の理由だと思います(公式の文章には、理由は書かれていません)。
- **`edit` は、一意に一致しないと失敗する**ので、**誤った場所を書き換える事故が起きにくい**。`sed` を AI に書かせると、正規表現の間違いで、広く壊れることがある。
- **ツールごとに、止める・許可する、を分けられる**。ハーネスから見て、`write` / `edit` は「パスが 1 つ」と分かりやすく、**検査しやすい**(`bash` は、文字列の解析が要る。[03](03-guards.md))。
- 画面での**表示**(差分が見やすい)。

### 「`ls`・`find`・`grep` は、`bash` があれば不要では?」
**そのとおりで、通常は不要です。** 公式の実装でも、`bash` があり、`grep`・`find`・`ls` が**ない**ときは、システムプロンプトに、**「ファイル操作(一覧・検索)には、bash で `ls`、`rg`、`find` を使え」**という規則が自動で入ります(`dist/core/system-prompt.js`)。つまり、**標準の構成は、「bash でやる」前提**です。

それでも、専用ツールを有効にする価値があるのは、次の場合です。
| 理由 | 内容 |
|---|---|
| **① 読み取り専用のエージェントを作れる** | **これが最大の理由です。** `pi --tools read,grep,find,ls` と起動すれば、**`bash` も `write` も、そもそも存在しない**エージェントになる。調査係・レビュー係(このリポジトリの `scout` / `reviewer`)が、この方式。`bash` がある限り、「読むだけ」は保証できない |
| ② 出力が、**上限つきで、整っている** | `grep`: 最大 100 件、`find`: 最大 1000 件、`ls`: 最大 500 件(いずれも 50 KB まで)。**`.gitignore` を尊重**する(`node_modules` などを、検索しない) |
| ③ AI が迷いにくい(私の推測) | 専用の引数(`pattern`、`glob`、`ignoreCase`、`context` など)で呼べるので、シェルの書き方を、間違えにくい |

**まとめ:** 1 つの万能なエージェントを、**そのまま動かす**だけなら、**4 つのままで十分**です。**役割ごとに、権限を分けたい**(読むだけの係を作る)なら、`grep`・`find`・`ls` が必要になります。

### 「ファイルの新規作成・削除・移動は、`bash` の中?」
**はい。**
| 操作 | 使うもの |
|---|---|
| 新規作成 | `write`(内容つき)、または `bash` の `touch`、`mkdir` |
| 上書き | `write` |
| 一部を修正 | `edit` |
| **削除** | **`bash` の `rm`**(専用ツールは、ない) |
| **移動・名前変更** | **`bash` の `mv`**(専用ツールは、ない) |
| コピー | **`bash` の `cp`** |
| `git`、`npm`、テストの実行など | **`bash`** |

**ここが危険の源です。** 削除・移動・インストール・`git push` は、**すべて `bash` を通る**ので、**`bash` を見張れば、危険の大部分を押さえられます**。このハーネスのガード([03](03-guards.md))が、`bash` の検査に力を入れているのは、このためです。

## 2. `AGENTS.md` は、設定しないと読まれないのか

**いいえ。設定なしで、自動で読まれます。** (公式 `configuration.md`、実装 `resource-loader.js`)

| 項目 | 内容 |
|---|---|
| 読まれるファイル名 | `AGENTS.md`(正式)。ほかに、`AGENTS.override.md`、`AGENTS.MD`、`CLAUDE.md`、`CLAUDE.MD` |
| **1 つのフォルダでは、1 つだけ** | 優先順位は **`AGENTS.override.md` > `AGENTS.md` > `AGENTS.MD` > `CLAUDE.md` > `CLAUDE.MD`**。同じフォルダに `AGENTS.md` と `CLAUDE.md` が両方あれば、**`AGENTS.md` だけ**が読まれる |
| 探す場所 | ① `~/.pi/agent/`(全体用) ② **作業フォルダ**と、その**親フォルダを、ルートまで** |
| 読む順序 | ① 全体用 → ② 親から子へ(**作業フォルダに近いほど、後ろ**)。**全部、連結**されて、モデルに渡される |
| 信頼(trust)の確認 | **不要**(信頼の対象外。常に読まれる) |
| 読ませない | 起動時に `-nc`(`--no-context-files`) |
| 反映 | 編集したら、Pi の中で `/reload` |

- つまり、**Claude Code の `CLAUDE.md` を、そのまま Pi も読みます**(`AGENTS.md` が無ければ)。Codex・OpenCode の `AGENTS.md` も同じ。**1 つのファイルを、複数のツールで共有**できます。
- 「ファイル名は `agent.md`」ではなく、**`AGENTS.md`(複数形、大文字)**です。
- ⚠️ 公式は、**「`AGENTS.md` の中身は、信頼できない入力として扱え」**と注意しています。知らないリポジトリの `AGENTS.md` には、AI への悪意のある指示が入っているかもしれません(プロンプトインジェクション)。
- ⚠️ **`AGENTS.md` は「お願い」であって、「強制」ではありません。** 「`rm -rf` するな」と書いても、守られる保証はない([README](README.md)の基本方針)。

## 3. 確認なしで何でも実行できる。どう制御するか

まず、**事実**を整理します。

### 3.1 何が「危険」なのか(実装・公式で確認)
- Pi は、**起動したユーザーの権限で、何でもできる**(公式 `security.md`)。ホームの下を消す、秘密のファイルを読む、ネットワークに送る、すべて可能。
- **`bash` は、Pi の環境変数を、そのまま引き継ぐ**(実装: `getShellEnv()` が `process.env` を渡す)。**`ANTHROPIC_API_KEY` などを環境変数で渡していると、AI の実行するコマンドから、見えます**(`env` や `printenv`)。
- 公式の立場: **「サンドボックスが組み込まれていないこと」は、想定どおりで、脆弱性ではない**(`security.md`)。**守るのは、利用者の責任。**

### 3.2 制御の 3 つの方法と、実践者の考え方
| 方法 | 内容 | 強さ |
|---|---|---|
| **A. 確認ダイアログ**(許可制) | 危険なコマンドの前に、人に聞く | **弱い**。人が見落とす。無人運転では使えない |
| **B. ガード**(拡張で、コードによる拒否) | 危険な操作を、**コードで、自動で拒否**する | 中。**書き方しだいで、すり抜けがある** |
| **C. 隔離**(サンドボックス・コンテナ・VM) | AI が触れる範囲そのものを、**OS・VM で、制限**する | **強い**。公式も、「通常、いちばん強い実用的な選択」と書く |

- **実践者(Pi の作者 Mario Zechner)の考え方**(実践者): 確認ダイアログは「ほぼ、セキュリティの芝居」。**確認ではなく、外側の隔離で守る**(「YOLO + コンテナ」)。
- **このハーネスの方針**: B(ガード)を作り、C(隔離)は**未実装**(最大の穴)。**A は最小限**。
- 公式の最小例(`examples/extensions/permission-gate.ts`)は、`rm -rf`、`sudo`、`chmod 777` を、**正規表現で探して**確認する簡単なもので、**`sh -c '...'` や変数経由などで、すり抜けられます**。そのため、このハーネスは、**シェルを解析する方式**にしました([03](03-guards.md))。

### 3.3 一言でいうと
**「ガード(B)は、事故を減らす。本当の安全は、隔離(C)で作る。」** 順に、両方を入れます。

## 4. システム開発で、よく使われる設定の一覧

「誰もが、必ず入れる」というものではなく、**実践者と公式の情報から、よく挙がるもの**を、重要度順に並べます。**重要度は、私の判断**です。

### 凡例
- ◎ = 最初から入れたい(安全・基本)
- ○ = 使い始めたら入れる
- △ = 必要になったら

### 4.1 一覧表

| # | 設定 | 何のため | 置き場所 | 重要度 |
|---|---|---|---|---|
| 1 | **作業は、バージョン管理(git)の中で** | いつでも元に戻せる。**最大の保険** | プロジェクト | ◎ |
| 2 | **`AGENTS.md`** にプロジェクトの約束事 | ビルド・テストの方法、規約を伝える | プロジェクト直下 | ◎ |
| 3 | **`main` ブランチの保護**(GitHub のルールセット) | 直接 push・force push・削除を、GitHub 側で禁止 | GitHub の設定 | ◎ |
| 4 | **`git push` を止める** | AI が、勝手に公開しない | 拡張(ガード) | ◎ |
| 5 | **秘密を AI から見えなくする** | キー・トークンの流出を防ぐ | 環境変数、`.env` の扱い、拡張 | ◎ |
| 6 | **隔離(コンテナ・VM)** | 事故・攻撃の被害を、閉じ込める | Docker など | ◎(無人運転なら必須) |
| 7 | **危険コマンドの拒否**(`rm -rf`、`sudo`、システムへのインストール) | 取り返しのつかない操作を止める | 拡張(ガード) | ◎ |
| 8 | **プロジェクトの信頼**(`defaultProjectTrust`) | 知らないリポジトリの拡張が、勝手に動かない | `~/.pi/agent/settings.json` | ○ |
| 9 | **使うツールの絞り込み**(`defaultTools`) | 役割に応じて、権限を最小にする | `settings.json`、`--tools` | ○ |
| 10 | **モデルの選択肢**(`enabledModels`、`defaultModel`) | 使うモデルの限定、費用の管理 | `settings.json` | ○ |
| 11 | **検証コマンド**(lint・型・テスト)を、1 つにまとめる | 「できた」を機械で確かめる | `package.json` の `check` | ○ |
| 12 | **CI**(GitHub Actions) | マージ前に、自動で検証 | `.github/workflows/` | ○ |
| 13 | **作業ブランチ + 小さなコミット** | レビューしやすく、戻しやすい | 運用、拡張(ガード) | ○ |
| 14 | **使用額・使用率の確認** | 費用の暴走に気づく | 画面下のステータス、`/session` | ○ |
| 15 | **要約(compaction)の設定** | 長い作業で、文脈が溢れても続ける | `settings.json` | △ |
| 16 | **`/login` の認証情報の保護**(`auth.json`) | 鍵の漏洩を防ぐ | `~/.pi/agent/auth.json`(権限 600) | ○ |
| 17 | **スキル・プロンプトテンプレート** | 定型作業を、再利用 | `skills/`、`prompts/` | △ |
| 18 | **サブエージェント・計画・自律ループ** | 長い作業の自動化 | 拡張 | △(最初は不要) |
| 19 | **依存関係の更新の自動化**(Dependabot) | 古い依存の脆弱性を防ぐ | `.github/dependabot.yml` | △ |
| 20 | **セッションの共有に注意**(`/share`、`/export`) | 秘密が、会話に残っている | 運用 | ○ |

### 4.2 各項目の「どこに、どう設定するか」

#### 1. バージョン管理の中で作業する(◎)
- やり方: 作業フォルダで `git init`(または既存のリポジトリ)。**作業を始める前に、コミット**する。
- 理由: AI は、ファイルを**確認なしで上書き・削除**する。**git があれば、戻せる**。公式も、「大事な作業の前に、バージョン管理かバックアップを」と書いている(`quickstart.md`、`security.md`)。
- 作業は、**別のブランチ**(`git switch -c feat/xxx`)で行う(#13)。

#### 2. `AGENTS.md`(◎)
- 場所: プロジェクト直下の `AGENTS.md`。全プロジェクト共通は `~/.pi/agent/AGENTS.md`。
- 書く内容の例(短く、具体的に):
  ```markdown
  # プロジェクトの約束事
  - 検証: `npm run check`(lint・型・テスト)。変更したら、必ず実行する。
  - ブランチ: `main` に直接コミットしない。`feat/…` で作業する。
  - コミットメッセージ: 日本語、1 行目は 50 文字以内。
  - テストの skip・削除で、通さない。
  ```
- ⚠️ 「お願い」であって、強制ではない。**守らせたいものは、#4・#7 のガードに移す**。

#### 3. `main` ブランチの保護(◎)
- 場所: **GitHub**のリポジトリ設定 → Rules → Rulesets(または Branch protection)。
- 内容: **PR 必須、force push 禁止、削除禁止**、(あれば)必須のステータスチェック。
- 理由: **AI が、`git push` のガードをすり抜けても、GitHub が止める**。**ハーネスの外側の、別の壁**。
- このハーネスは、`harness_ensure_protection` で、確認のうえ設定できる([08](08-verify-review-pr.md))。
- ⚠️ 設定には、**リポジトリの管理者の権限**が必要。

#### 4・7. ガード(拡張)(◎)
- 場所: `~/.pi/agent/extensions/名前.ts`(または `名前/index.ts`)。
- 内容: `tool_call` イベントで、`bash` の `git push`、`rm -rf`、`sudo`、`npm install -g`、秘密のファイルへの `write` / `edit` などを、`{ block: true, reason }` で拒否。
- 最初は、**公式のサンプルを置く**(`examples/extensions/permission-gate.ts`、`protected-paths.ts`)。**ただし、正規表現の簡易版なので、すり抜けがある**ことを理解したうえで。
- 本格的なものは、**このリポジトリの `guards/`**([03](03-guards.md))。

#### 5. 秘密を AI から見えなくする(◎)
- **環境変数のキーは、`bash` から見える**(3.1)。対策:
  - 認証は、環境変数ではなく **`/login`(`auth.json`)**を使う。`bash` のプロセスには、`auth.json` の中身は渡らない(**ただし、ファイルとしては、AI が `cat ~/.pi/agent/auth.json` で読める**。だから、ガードで、`~/.pi/agent` の読み取りを止める。このハーネスの `secrets.ts`)。
  - **最も確実なのは、隔離環境の中に、そもそも秘密を入れない**こと(実践者の共通の知恵: ホスト側のプロキシが、外向きの通信でキーを差し込む。Docker Sandboxes、Gondolin など)。
- `.env`、`*.pem`、SSH の鍵は、**AI に読ませない**(ガード)。リポジトリには、`.env.example` だけを置く。
- `auth.json` は、**権限 600**(`chmod 600 ~/.pi/agent/auth.json`)。リポジトリに**入れない**。

#### 6. 隔離(◎、無人運転なら必須)
公式が挙げる方法(`containerization.md`):
| 方法 | 隔離されるもの | 秘密の扱い | 向く場面 |
|---|---|---|---|
| **Docker(素)** | Pi 全体、ツール、拡張 | コンテナに渡した変数は見える | いちばん簡単な、コンテナの境界 |
| **Docker Sandboxes** | Pi 全体 | **本物のキーは、ホストに残り、プロキシが差し込む** | キーを中に入れたくない |
| **OpenShell** | Pi 全体 | ポリシーで制御 | ファイル・プロセス・ネットワーク・秘密を、ポリシーで |
| **Gondolin 拡張** | **組み込みツールと `!` コマンドだけ**(Pi 本体と他の拡張は、ホスト) | 保存された認証はホスト。**コマンドは、ホストの環境変数を引き継ぐ** | ホストの画面のまま、コマンドだけ隔離 |
- 共通の注意(公式): **作業フォルダだけを、マウント**する。**`~/.pi/agent` をマウントしない**(認証が見える)。**必要なネットワークだけ**開ける。
- このリポジトリでは、**未実装**です([../sandbox-options.md](../sandbox-options.md))。まず、**素の Docker**(公式の `Dockerfile.pi` の例)で、「コンテナの中で Pi を動かす」から始めるのが、いちばん簡単です。

#### 8. プロジェクトの信頼(○)
- 場所: `~/.pi/agent/settings.json`(**ユーザー設定にだけ**書ける)。
  ```json
  { "defaultProjectTrust": "ask" }
  ```
  - `"ask"`(既定): 聞く。`"never"`: 常に、読み込まない。`"always"`: 常に読み込む(**自分のリポジトリだけを使うなら可。知らないものを開くなら避ける**)。
- 画面のない実行(`-p` など)では、`ask` は「読み込まない」になる。

#### 9. 使うツールの絞り込み(○)
- 場所: `settings.json` の `defaultTools`、または起動時の `--tools`。
  ```json
  { "defaultTools": ["read", "bash", "edit", "write", "grep", "find", "ls"] }
  ```
  (名前だけを書くと、**標準を置き換える**。`"+grep"` のように `+` をつけると、**標準に追加**。`"-bash"` で、除く。)
- **読み取り専用**: `pi --tools read,grep,find,ls`。レビューや調査に。

#### 10. モデルの選択肢(○)
- 場所: `settings.json`。このリポジトリの例:
  ```json
  { "enabledModels": ["opencode-go/*", "anthropic/claude-sonnet-5-5", "openai-codex/*"] }
  ```
  `defaultProvider` / `defaultModel` で、起動時のモデルも指定できる。`/model` で、画面から保存もできる(`Ctrl+S`)。

#### 11・12. 検証コマンドと CI(○)
- `package.json`:
  ```json
  { "scripts": { "check": "biome check . && tsc --noEmit && node --test" } }
  ```
  **1 つのコマンドで、lint・型・テストを回せる**ようにする。AI にも、人にも、「これを通せ」と言える。
- CI: `.github/workflows/quality.yml` で、**同じ `npm run check`** を実行。ジョブ名を、ブランチ保護の**必須チェック**に登録する(#3)。
- スキル `nix-setup` は、これらをまとめて作る([09](09-compaction-skills-install.md))。

#### 14. 使用額・使用率の確認(○)
- 画面下に、**文脈の使用量と、累計の使用額・費用**が出る(公式 `usage.md`)。`/session` で詳細。
- Go・Codex の使用率は、拡張で取得する([05](05-models-and-usage.md))。
- 無人運転では、**予算の上限**(回数・時間)を、ループに持たせる([07](07-plan-and-loop.md))。

#### 15. 要約(△)
- `settings.json`:
  ```json
  { "compaction": { "enabled": true, "reserveTokens": 16384, "keepRecentTokens": 20000 } }
  ```
  標準のままでも、動く。長い作業で、重要な情報が失われるなら、拡張で要約を制御([09](09-compaction-skills-install.md))。

#### 20. セッションの共有に注意(○)
- `/share`(アップロード)・`/export`・`/debug` は、**会話の全部**(プロンプト、コマンドの出力、ファイルの中身、**流出した鍵も**)を含む。**出す前に、中身を確認**。

## 5. 最小の安全設定(まず、これだけ)

**最初の 1 週間**に、これだけ入れておけば、「確認なし」の怖さは、かなり減ります。

1. 作業は、**git で管理されたフォルダ**で、**作業ブランチ**を切って行う。
2. GitHub で、**`main` を保護**する(PR 必須、force push・削除の禁止)。
3. **Pi は、Docker のコンテナの中で動かす**(作業フォルダだけをマウント。`~/.pi/agent` は、マウントしない。キーは、必要なものだけを、環境変数で渡す)。
4. `AGENTS.md` に、**検証コマンドと、ブランチの規約**を書く。
5. 拡張で、**`git push`、`rm -rf`、`sudo`、`.env` の書き込みを、拒否**する(公式サンプルから始め、このリポジトリの `guards/` に進む)。
6. `defaultProjectTrust` は、`ask` のまま。**知らないリポジトリは、信頼しない**。
7. `/share` は、**中身を確認してから**。
