# 10 テストの読み方: ルールが守られていることを、どう確かめるか

## ねらい
ガードやループは、**間違えると、事故になる**部品です。このハーネスが、どうやって「動く」ことを確かめているか(ユニットテスト、実際の Pi を使った統合テスト)と、**テスト自体を信頼する方法**を理解します。

## 何を作ったか
| ファイル | 内容 |
|---|---|
| `tests/helpers.ts` | テスト用の設定(`config`)、ガードの入力を作る `input()`、コマンドを解析する `inv()` |
| `tests/shell.test.ts` | シェルの解析器 |
| `tests/git-guard.test.ts`・`fs-guard.test.ts`・`install-guard.test.ts`・`secrets-guard.test.ts`・`guards-index.test.ts` | 各ガード |
| `tests/git-state.test.ts`・`config.test.ts` | git の状態、設定の読み込み |
| `tests/plan.test.ts`・`verify.test.ts`・`pr.test.ts`・`git-tools.test.ts` | 計画・検証・レビュー・PR のゲート、worktree |
| `tests/final-line.test.ts`・`models.test.ts`・`usage.test.ts`・`subagent.test.ts`・`compaction.test.ts`・`assets.test.ts` | 周辺機能 |
| `tests/e2e.test.ts` | **実際の Pi を起動する統合テスト** |
| `.github/workflows/quality.yml` | CI(ジョブ名 `quality`)。`npm run check` を実行 |

`npm run check` = `biome check .`(lint・format)+ `tsc --noEmit`(型)+ `node --test`(テスト、176 件)。テストは、Node 標準のテストランナー(`node:test`)で、**追加のライブラリなし**です。

## 仕組み

### 1. ユニットテスト: 純粋関数を、表のように
ガードや状態機械が、**純粋関数**([README](README.md))なので、Pi なしで、入力と出力だけを確かめられます。
```ts
// 考え方(実際のコードは tests/git-guard.test.ts)
assert.equal(checkGit(inv("git push --force origin feat/x"), input({})).kind, "block");
assert.equal(checkGit(inv("git push origin feat/x"),         input({})).kind, "allow");
assert.equal(checkGit(inv("git push origin main"),           input({})).kind, "block");
```
`helpers.ts` の `input({ branch, cwd, subagent, ... })` で、**「どのブランチにいて、サブエージェントか」**といった状況を、1 行で作ります。
**テストは、仕様書**です。「何を通し、何を止めるか」が、例として並びます。

### 2. 統合テスト: 実際の Pi を、偽のモデルで動かす(`e2e.test.ts`)
ユニットテストが通っても、**Pi と正しくつながっているか**(イベントの名前、戻り値の形、読み込み)は、別の話です。そこで、**実際の Pi(`node_modules` の 1.5.2)を、RPC モードで起動**します。
```
テスト ──(RPC: 標準入出力)──→ 実際の Pi(ハーネスを読み込み済み)
                                    │ モデルの呼び出し
                                    ↓
                           偽のモデル(ローカルの、OpenAI 互換サーバー)
                           台本: [{ tool: "bash", args: {...} }, { text: "..." }, ...]
```
- 偽のモデルは、**台本どおりに**、ツール呼び出しや、テキストを返す(ネットワークも、API キーも、不要)
- テストが、台本を渡し、Pi の**出力イベント**と、偽のモデルが**受け取ったメッセージ**を、検査する

**場面 1(ガード・計画・ループ・最終行)**: 拡張が読み込まれる → `git push --force` がガードで拒否され、理由がモデルに返る → 計画を提出・確定(`extension_ui_response` で、画面の応答を、テストが返す) → 確定後に `ask_user` が消える → 自律ループが、継続メッセージを送る → 完了報告 → 最終行が付く
**場面 2(サブエージェント)**: `subagent` ツールが、独立した `pi` の子プロセスを起動する → 子には、ハーネスの拡張だけ → 子は、読み取り専用のツールだけ → 報告が、親に返る

### 3. テストを、信頼できるものにする
テストが**通る**ことは、「テストが**正しい**」ことを意味しません。次を、行いました。
- **変異の確認**: 実装の重要な部分を、わざと壊し、**テストが落ちる**ことを確かめる(落ちなければ、そのテストは、何も守っていない)
- **実際の Pi で見つかったバグ**(ユニットテストでは、見つからなかった):
  - サブエージェントの既定のモデルが、`session_start` の復元処理で、**上書きされていた** → `rt.subagentModelDefault` を導入して修正
  - `--list-models` を使った確認が、**不安定**(環境で結果が変わる) → RPC の `get_commands` で、確認する形に置き換え
  - Biome が、テンプレートの中の `biome.json` を、**設定として読んでしまった** → テンプレートの名前を `biome.json.template` に変更

### 4. CI(`quality`)
プルリクエストごとに、`npm ci --ignore-scripts` → `npm run check` を実行。**ジョブ名 `quality`** は、GitHub のブランチ保護の、**必須のチェック名**と一致させています(`nix-setup` のスキルも、同じ名前)([08](08-verify-review-pr.md))。

## なぜこう実装したか
| 選んだこと | 却下した案 | 理由 |
|---|---|---|
| **純粋関数 + 薄い接続部** | `register.ts` に、直接書く | ユニットテストで、**網羅的に**確かめられる。ガードの**抜け**は、事故に直結する |
| **実際の Pi を使う統合テスト** | モックの Pi API だけ | モックは、**自分の理解を、テストするだけ**。Pi の実際の挙動(イベントの順序、例外時の挙動)は、実物でしか分からない。実際に、**バグが見つかった** |
| **偽のモデルで台本を動かす** | 実際のモデルを使う | **決定論的**(毎回同じ)で、**無料**で、**ネットワーク不要**。CI でも回る |
| **Node 標準のテストランナー** | Jest / Vitest | 依存を増やさない。TypeScript は、Node が直接実行できる(`erasableSyntaxOnly`) |
| **Pi の版を固定**(1.5.2) | 最新を追う | 拡張の API は、更新で変わる。**統合テストが、「この版で動く」ことの証明**。更新は、Dependabot の PR で、テストを通して、確認する |
| **変異の確認** | テストが緑なら、よし | 緑のテストは、**何も確かめていない**可能性がある |

## Claude Code では
| 観点 | Claude Code(フックなど) | このハーネス |
|---|---|---|
| フックのテスト | フックは、**外部コマンド**。標準入力に JSON を渡し、終了コードと出力を確認する、**単純な形**で、自分でテストする(未確認:公式のテスト用ツールは、確認できず) | 純粋関数のユニットテスト + 実際の Pi の統合テスト |
| 言語 | 何でもよい(シェル、Python など) | TypeScript |
| 実物での検証 | 実際の Claude Code を起動して、確かめる。**モデルを偽物にするのは、公式の仕組みとしては、確認できず**(未確認) | **偽のモデルの、ローカルサーバー**で、実物の Pi を動かす(Pi が、プロバイダの URL を、設定で変えられるため) |
| 継続的な確認 | CI に、自分で組み込む | `quality` |

**違いの要点:**
- Claude Code のフックは、**入出力が単純**(JSON と終了コード)なので、テストは書きやすいが、**状態を持つ処理**(計画・ループ)は、自分で保存して、管理する必要がある。
- Pi の拡張は、**状態もロジックも、コードの中**。その分、**テストの量と、質**が、品質を決める。このハーネスが、**純粋関数と接続部を分けた**のは、そのため。
- どちらの場合も、**「実物で、通しで動かす」テスト**は、価値が高い。ユニットテストが全部通っていても、**つなぎ目で、壊れる**ことがある。

## 試してみよう
1. `npm test` を実行し、**どのテストが、何件**あるかを見る。`node --test tests/plan.test.ts` で、1 ファイルだけ実行する。
2. **変異の確認を、自分でやる**: `guards/git.ts` の `checkPush` で、`FORCE_FLAGS` から `"-f"` を消す → `node --test tests/git-guard.test.ts` → **落ちるテストを、確認**する。元に戻す(`git checkout agent/extensions/harness/guards/git.ts`)。
3. `tests/e2e.test.ts` の台本(`Step` の並び)を読み、場面 1 の流れを、紙に書く。**偽のモデルが、どのタイミングで、何を返しているか**を、説明できるか。
4. e2e に、**新しい場面**を足す: 「`.env` を作ろうとして、拒否される」。台本は、`{ tool: "write", args: { path: ".env", content: "KEY=1" } }` のあと、`{ text: "..." }`。**拒否の理由が、モデルに返っている**ことを、検査する。
5. 新しいガードを足したら、**まず、落ちるテストを書く**(止めたいコマンドが、止まらないテスト)。そのあと、ガードを書いて、緑にする。

## 限界と注意
- 統合テストは、**偽のモデル**。**実際の LLM が、ガードの拒否の理由を読んで、うまく代わりの手段を選べるか**は、テストできていない。
- GitHub・OpenCode Go・Codex との実際の通信は、テスト対象外(パーサーは、想定した JSON でテスト済みだが、**実際のレスポンスとの一致は、未検証**)。
- シェルの解析器は、**テストした書き方**に対して、正しい。未知の書き方で、すり抜ける可能性は、**常に**ある(サブエージェント、サンドボックスで補う)。
- テストの数(176 件)は、品質の証明では**ない**。大切なのは、**何を、守っているか**。
