# 07 計画と自律ループ: 決めた計画を、止まらずに完走させる

## ねらい
このハーネスの、もう 1 つの中心です。**ユーザーと計画を確定させ、確定後は質問せずに、完了まで自動で進める**仕組みと、その**暴走を止める仕組み**を理解します。

## 何を作ったか
| ファイル | 役割 |
|---|---|
| `flow/plan.ts`(334 行) | **計画の状態機械**(純粋関数)。項目の状態、完了のゲート、差し戻しの数え方 |
| `flow/loop.ts`(96 行) | **「継続するか」の判断**(純粋関数)。停止条件、継続のメッセージ |
| `flow/report.ts`(68 行) | 完了報告の組み立て(純粋関数) |
| `flow/register.ts`(571 行) | Pi への接続。`ask_user`・`plan_*` ツール、`agent_before_settle`、`/plan` |
| `lib/state.ts` | セッションのエントリへの保存と復元 |

## 仕組み

### 1. Plan → Do → Check → Act
`instructions/main.md`([04](04-instructions-and-output.md))で、AI に渡している進め方です。

| 段階 | AI がすること | ハーネスが強制すること |
|---|---|---|
| **Plan** | `ask_user` で、要件・完了条件・判断の基準を、ユーザーと確認 → `plan_propose` で、チェックリストを提出 | ユーザーが「確定する」を選ぶまで、計画は有効にならない。完了条件が空の項目は、受け付けない |
| **Do** | **質問せずに**、項目を 1 つずつ進め、`plan_update` で更新 | 確定後は、`ask_user` を、**ツールの一覧から外す**(`setActiveTools`) |
| **Check** | `harness_verify`(検証)、`harness_review`(独立レビュー)([08](08-verify-review-pr.md)) | 完了にするには、証拠・検証・レビューが必要(下記のゲート) |
| **Act** | 失敗を直して、Check をやり直す | 差し戻しを数え、3 周で、その項目は「未完了」にして、次へ進める |

### 2. 計画の状態(`Plan`)
```
goal / confirmed / items[] / paused / continuations / startedAt /
progressKey / noProgress / decisions[] / verifications[] / reviews[] / prs[]
```
項目(`PlanItem`)の状態は 5 つ: `pending`(未着手) → `in_progress`(進行中) → `done`(完了) / `unfinished`(未完了) / `deferred`(保留)。
- `kind`: `change`(ファイルを変更する → **検証が必要**)/ `task`(調査・記録)
- `review`: true なら、**独立レビューが必要**
- `cycles`: 差し戻された回数

状態は、**`pi.appendEntry("harness-plan", plan)` で保存**され、復元されます。

### 3. 完了のゲート(`updateItem`)
モデルが「完了」と言うだけでは、**完了になりません**。`plan_update(done)` は、次をすべて満たすときだけ通ります。

```
1. 計画が確定している
2. 根拠(evidence: file:line、コマンドの出力)が書かれている
3. kind が change なら:
     検証が実行済み + 成功 + 「検証したときの指紋」が「いまの作業ツリーの指紋」と同じ
4. review が true なら:
     レビュー済み + 承認 + 指紋が同じ
```
**指紋(fingerprint)**: 作業ツリーのファイルの内容から作るハッシュ(`flow/fingerprint.ts`)。コミットの有無に左右されません。検証のあとに、1 文字でも変更されると、指紋が変わり、**「最後の変更のあとに検証していない」と分かる**。

### 4. 自律ループ(`agent_before_settle`)
Pi には、**エージェントが、本当に終わる直前**に、`agent_before_settle` というフックがあります。ここで `{ continue: true, entries: [...] }` を返すと、**もう 1 回、実行を続けさせられます**。

```
AI が、ツール呼び出しなしで、応答を終える
   ↓
agent_before_settle
   ↓ decideContinuation(plan, now, limits, killSwitch)  ← 純粋関数
   ├─ 継続しない: 計画なし / 完了 / 一時停止 / キルスイッチ / 上限 → そのまま終わる
   └─ 継続する: 「確定した計画は、まだ完了していません。ユーザーに質問せずに、続けてください。
                 (チェックリスト) 次に取り組む項目: ...」を、モデルに渡して、続行
   ↓ (繰り返し)
すべての項目が済んだ → 「plan_report を呼び、完了報告を出してください」を、1 回だけ渡す
```

### 5. 暴走を止める 6 つの条件(`decideContinuation`)
無条件に継続すると、無限ループになります。次の条件で、**必ず止まります**。

| 条件 | 内容 | 止まり方 |
|---|---|---|
| 計画が確定していない | 通常の会話では、ループしない | 何もしない |
| **キルスイッチ** | ファイル `<設定ディレクトリ>/harness-off` がある | 継続しない(ファイルを作るだけで、止められる) |
| 一時停止 | Esc で中断した、`/plan stop`、上限に達した | 継続しない。`/plan resume` で再開 |
| 完了 | 未着手・進行中の項目が 0 | 完了報告を促して、終わる |
| **継続の上限** | 200 回 | 一時停止にして、通知 |
| **時間の上限** | 240 分 | 同上 |
| **進捗がない** | 継続のたびに、`progressKey`(項目の状態・差し戻し・記録の数)が、**同じ**まま 3 回続く | 同上 |

さらに、**項目ごと**に、差し戻しが 3 周で収まらなければ、その項目を「未完了」にして**次へ進みます**(止まらずに、他を進める)。

### 6. 中断(Esc)
`agent_settled` で `event.aborted` なら、**自動で継続せず、一時停止**にします(人間が止めたい意思を尊重)。`/plan resume` で再開。

### 7. 計画を忘れさせない
`before_agent_start` で、**確定済みで未完了の計画を、毎回システムプロンプトに載せます**(`<harness_plan>`)。長い会話の途中や、要約([09](09-compaction-skills-install.md))のあとでも、計画を見失いません。

### 8. ユーザーのコマンド
- `/plan`: 現在の状況を表示
- `/plan stop`: 止める
- `/plan resume`: 再開(継続のメッセージを、すぐ送って、実行を始める)

## なぜこう実装したか
| 選んだこと | 却下した案 | 理由 |
|---|---|---|
| **計画を、確定させてから、質問を止める** | 最初から、質問を禁止 | 要件が曖昧なまま走ると、**間違った物を、完璧に作る**。判断はここで集め、あとは走らせる(要件の核心) |
| **確定後は、`ask_user` ツールを外す** | 「質問するな」と指示する | 指示は破られうる。**ツールがなければ、質問できない**。画面がない環境でも、同じ |
| **完了を、ゲートで判定** | AI の「完了しました」を信じる | 「できたつもり」が、いちばん多い失敗。**証拠・検証・レビューを、状態で確かめる** |
| **指紋で、「最後の変更のあと」を判定** | コミットの有無、時刻 | 未コミットの変更や、時計のずれに左右されない。**中身が同じなら、同じ**という、単純な性質 |
| **継続に、複数の上限を設けた** | 1 つの上限(回数)だけ | 回数が少なくても、1 回が長い、同じことを繰り返す、など、**暴走の形は、さまざま**。回数・時間・進捗の 3 つで受ける |
| **止まるときは、「一時停止」にして、再開できる** | 終了する | 上限で止まっても、**状態が残り、人間が見て、再開できる** |
| **3 周で収まらない項目は、未完了で次へ** | 全体を止める | 無人運転では、**1 つの項目に、全体が引きずられない**ほうがよい。最後に、未完了として報告される |
| **判断を、純粋関数に集めた** | `register.ts` に、直接書く | **ループの安全性**は、いちばんテストしたい所。Pi なしで、条件を網羅できる(`tests/plan.test.ts`) |
| **キルスイッチを、ファイルにした** | コマンドだけ | 別の端末や、スクリプトからも、**今すぐ止められる** |
| **完了報告を、`plan_report` の出力で、機械的に作る** | AI に、自由に書かせる | 要件ごとの完了・未完了、検証・レビューの結果が、**漏れなく、同じ形**で出る |

## Claude Code では
(公式ドキュメントで確認した内容)

| 観点 | Claude Code | このハーネス |
|---|---|---|
| 計画 | **plan モード**(権限モード)。計画を提示 → ユーザーが承認 → 実行。`TodoWrite` ツール(未確認:細部) | `plan_propose`(ユーザーの確定が必須)+ 状態機械 |
| 止まらずに続ける | **`Stop` フック**: 終了コード 2、または `decision: "block"` + 理由で、**続けさせる**。無限ループを避けるため、入力の `stop_hook_active` で、すでに継続中かが分かる(未確認:細部) | `agent_before_settle` で `continue: true` |
| 目標の完了まで | **`/goal <条件>`**: Stop フックの、**組み込みのラッパー**。小さな評価モデルが、「条件を満たしたか」を判定(`met` / `not met` / `impossible`)。ツールを呼ばない評価で、**数ターン、ツール呼び出しがないと止まる**。条件は、4000 文字まで | 状態機械(項目・ゲート)で判定。**判定は、コード**(モデルではない) |
| 完了の判定 | **評価モデル**が、会話の内容から、条件を判断する | **作業ツリーの指紋・検証・レビューの記録**で、決定論的に判断 |
| 質問を止める | 権限モードで、確認を減らす(`auto`、`bypassPermissions`)。質問(`AskUserQuestion`)を止める機構は、未確認 | `ask_user` を、ツール一覧から外す |
| 中断 | Esc で中断 | `aborted` で一時停止。再開できる |
| 暴走の上限 | `/goal` は、無進捗で止まる(数ターン)。そのほか(未確認) | 回数・時間・進捗・キルスイッチ |

**違いの要点:**
- Claude Code の `/goal` は、**とても似た考え**(確定した目標を、完了まで走らせる)。違いは、**完了の判定**。
  - `/goal`: **別のモデル**が「満たしたか」を判断する。**柔軟**で、書くのも楽(自然な文章)。ただし、判断は**確率的**で、評価モデルも誤りうる。
  - このハーネス: **コード**が、証拠・検証・レビューの**記録**で判断する。**決定論的**で、嘘をつかせにくい。ただし、**計画の項目を、細かく書く**手間がかかり、**定義した種類の確認しか、できない**。
- どちらが良いかは、**用途しだい**。「計画が明確で、検証コマンドが整っている」作業は、ハーネスの方式が向き、「目標が曖昧で、柔軟な判断が要る」作業は、`/goal` が向く。
- 両方に共通する大事な点は、**「終わろうとしたときに、検査して、足りなければ続けさせる」**という、**終了の境界**に、フックを置くこと。Claude Code の `Stop`、Pi の `agent_before_settle` です。

## 試してみよう
1. 試用環境で、「README.md を作って。計画を立ててから進めて」と頼む。**`ask_user` の質問 → 計画の確認 → 確定後は、質問が出ない**流れを観察する。
2. 進行中に、`/plan` で、チェックリストを見る。`/plan stop` で止め、`/plan resume` で再開する。
3. 計画が走っている間に、`touch ~/pi-trial/harness-off` を実行する(`<設定ディレクトリ>/harness-off`)。**次の継続で止まる**のを確認し、ファイルを消す。
4. `tests/plan.test.ts` を読み、**ゲートの失敗する場合**(証拠なし、検証なし、指紋の不一致)を、全部挙げる。
5. `flow/loop.ts` の `maxNoProgress` を 1 にして、テストが、どう落ちるかを見る(**テストが、仕様を守っている**ことを体感)。元に戻す。
6. 設計の練習: 「項目ごとの、時間の上限」を足すには、**どのファイルの、どの関数**を、どう変えるか、紙に書く(ヒント: `Limits` と `decideContinuation`、`PlanItem` の開始時刻)。

## 限界と注意
- **実際の LLM での、長時間の無人運転は、未検証**。統合テストは、偽のモデルの台本で、継続・完了・停止を確認している([10](10-tests.md))。
- **計画の質に、依存する**: 完了条件(`acceptance`)が曖昧な項目は、ゲートが甘くなる。ゲートは、「検証が通った」ことしか、確かめない。**検証コマンドが、貧弱なプロジェクトでは、意味が薄い**。
- 検証コマンドがない場合は、「未検証」として完了にでき、**自動マージはしない**([08](08-verify-review-pr.md))。
- `/plan resume` で、再開すると、`noProgress` が 0 に戻る。**再開を繰り返すと、上限を迂回できる**(人間の操作なので、許容している)。
