# 06 サブエージェント: 別プロセスに作業を任せる

## ねらい
Pi には、サブエージェントが**標準では、ありません**。このハーネスが、どうやって作ったか(別プロセス方式)、**なぜ安全か**、Claude Code の組み込みのサブエージェントと何が違うかを理解します。

> 方式は、**暫定(A 案)**です。決定は保留中です([../decisions/009-subagent-hold.md](../decisions/009-subagent-hold.md)、[../subagent-design.md](../subagent-design.md))。

## 何を作ったか
| ファイル | 役割 |
|---|---|
| `subagent/register.ts`(159 行) | `subagent` ツールの定義。件数・同時数・cwd の検査、進捗の表示、費用の集計 |

## 仕組み

### 全体の流れ
```
メインの AI ──(subagent ツール: tasks=[{agent, title, task, cwd?}, ...])──→ ハーネス
   ハーネスが、タスクごとに、別の `pi` プロセスを起動:
     pi --mode json -p --no-session --no-extensions -e <harness の入口>
        --no-mcp --no-skills --no-prompt-templates
        --model <モデル> [--tools read,grep,find,ls] --append-system-prompt <役割の指示>
        "Task: <依頼>"
     環境変数: PI_SUBAGENT=1 / PI_SUBAGENT_ROLE / PI_SUBAGENT_MODEL
   子は、JSON のイベントを、標準出力に流す → 親が読み、最後の返答と費用を取り出す
   親は、全員分の報告を、1 つのツール結果として、メインの AI に返す
```

### 子を「安全」にしている 6 つのこと
1. **`--no-extensions -e <ハーネス>`**: 親の拡張を引き継がず、**ハーネスの拡張だけ**を読み込む。→ 子にも、ガード([03](03-guards.md))が効く
2. **`PI_SUBAGENT=1`**(環境変数): ガードが「サブエージェントである」ことを知り、`git commit` / `push` / `merge` / `rebase`、`gh pr ...`、`git worktree` を block する。**モデルは、環境変数を書き換えられない**(プロセスの外から渡される)
3. **`registerSubagent` の先頭で `if (rt.isSubagent) return`**: 子は `subagent` ツールを持たない → **入れ子にならない**(再帰の暴走を防ぐ)
4. **`--tools read,grep,find,ls`**(役割の定義の `tools:`): `scout` と `reviewer` は、**読み取り専用**。bash も write も、**ツール自体が存在しない**
5. **`--no-session`、標準入力を閉じる**: 子は、ユーザーに質問できない。会話も保存しない
6. **上限**: 一度に 8 件、同時に 4 件、1 件 900 秒、セッション全体で 64 件(`config.default.json`)。`cwd` は、作業ルート・自分が作った worktree の内側だけ

### 役割の定義(`agents/*.md`)
```md
---
name: reviewer
description: 独立レビュー担当。...(読み取り専用)
tools: read, grep, find, ls
---
(本文 = 役割の指示。--append-system-prompt で渡される)
```
`scout`(調査)・`planner`(計画)・`worker`(実装)・`reviewer`(独立レビュー)。`model:` を書けば、役割ごとにモデルを固定でき、なければ `/subagent-model` の値。

### 結果の取り込み
子は `--mode json` で、イベントを 1 行ずつ JSON で出します。親は、`message_end`(assistant)から、**最後の返答**(報告)・トークン数・**費用**(`usage.cost.total`)を集めます。費用は `rt.childCost` に足され、画面下の使用額([05](05-models-and-usage.md))に反映されます。出力は、50 KB で切ります(`OUTPUT_CAP`)。

## なぜこう実装したか
| 選んだこと | 却下した案 | 理由 |
|---|---|---|
| **別プロセス(`pi` を起動)** | 同じプロセスの内側で、新しいセッションを作る | **文脈と権限が、完全に分かれる**。子が暴走しても、親は無事。公式のサンプルも、この方式。Pi の内部 API に依存しにくい |
| **子にもハーネスの拡張を読ませる** | 子は、素のまま | 素の子は、`git push --force` も `rm -rf` も、止められない。**子こそ、ガードが必要** |
| **子の commit・push・PR を禁止** | 子にも許す | 変更の統合・レビュー・公開は、**親(と、ユーザー)の責任**。子は、任された作業と報告まで |
| **読み取り専用を、ツールの一覧で実現** | 指示で「ファイルを変更するな」と書く | 指示は破られうる。**ツールがなければ、できない**(決定論) |
| **入れ子を禁止** | 深さを制限して許す | 費用と時間の暴走、追跡の困難さを避ける。必要なら、親が、順に呼べばよい |
| **報告は、最後の返答だけを返す** | 子の途中経過を、全部返す | 親の文脈を、汚さない(トークンの節約)。**長い途中経過は、親にとって、ノイズ** |
| **`/subagent-model` の既定を安いモデルに** | 親と同じ | 重い作業を、安く回す([05](05-models-and-usage.md)) |
| **役割は、md ファイルで定義** | コードに埋め込む | 役割を足すのに、コードを触らなくてよい。誰でも読める |

### 採用しなかった方式(保留中)
[../subagent-design.md](../subagent-design.md) に、A(別プロセス)・B・C の比較があります。ユーザーは決めかねて、**A を暫定**としました。A の弱点: 起動が重い(プロセスごとに Pi の初期化)、親子で情報を共有しにくい(渡せるのは、依頼の文章だけ)。

## Claude Code では
(公式ドキュメントで確認した内容)

| 観点 | Claude Code | このハーネス(Pi) |
|---|---|---|
| 提供 | **組み込み**(`Agent` ツール) | 自作(別プロセス) |
| 定義 | `.claude/agents/*.md` の frontmatter(`name`、`description`、`tools`、`model`、`permissionMode`、`hooks` など) | `agents/*.md`(`name`、`description`、`tools`、`model` だけ) |
| 実行 | 同じ Claude Code の中の、**独立した文脈**。**背景**でも**前景**でも動く | **別プロセス**。呼び出しは、完了まで待つ(同期) |
| 並列 | 最大 20 まで並列に動かせる(公式の記載) | 同時 4(設定で変更) |
| 入れ子 | **深さ 3 まで**(公式の記載) | **禁止** |
| 権限 | 子も、**親の権限ルールとフックの対象**(フックは、子の中でも動く) | 子にも、**同じガード**を読み込ませる(`PI_SUBAGENT` で、より厳しく) |
| 再開 | **`SendMessage` で、続きを頼める**(文脈が残る) | **できない**(1 回きり。`--no-session`) |
| 結果 | **最終の報告だけ**が親に返る | 同じ(最後の返答だけ) |
| 画面の表示 | 進捗が表示される(**未確認:** 細部) | `setWidget` で「<題名>を実行中」を表示 |
| 終了のフック | `SubagentStop` フック | なし(ツールの結果として、親が受け取る) |

**違いの要点:**
- Claude Code は、**組み込みで、作り込まれている**(再開、背景実行、入れ子、フックの適用)。Pi の方式は、**素朴で、境界がはっきりしている**(プロセスの境界)。そのかわり、再開ができず、起動が重い。
- 安全の考え方は、両方、「子にも親と同じ制限を効かせる」。違いは、Claude Code は、**設定で**、このハーネスは、**環境変数 + 拡張で**。
- 大きな違い: **Claude Code の子は、親と同じプロセスの中**。このハーネスの子は、**OS のプロセスとして独立**している。将来、サンドボックスを入れるとき、**プロセス単位で隔離しやすい**のは、後者。ただし、**子が親のサンドボックスを、自動で引き継ぐわけではない**ので、起動時に、同じ隔離を、子にも適用する設計が要る(未実装)。

## 試してみよう
1. 試用環境の Pi で、「`scout` に、このリポジトリの構成を調べさせて」と頼む。画面に「<題名>を実行中」が出て、結果が返るのを見る。
2. `/subagent-model` で、モデルを変えて、もう一度。`/usage` で、サブエージェントの費用が、使用額に含まれるのを見る。
3. `agents/` に、`tester.md` を足す(`tools: read, grep, find, ls, bash` など)。`/reload` して、使えるか確認する。
4. 次を試して、**子が、止められる**のを確かめる(`worker` に頼む): 「作業が終わったら `git commit` して」→ block され、「変更は親に任せ」と返る。
5. `tests/subagent.test.ts` を読み、`buildChildArgs` が、どんな引数を作るかを見る。`--tools` が入る条件は?
6. `tests/e2e.test.ts` の、サブエージェントのシナリオを読み、**偽のモデルの台本で、実際の Pi の子プロセスを動かしている**ことを確認する([10](10-tests.md))。

## 限界と注意
- **方式は、暫定**。起動の重さ、再開できない点が、実運用でどう効くかは、未検証。
- 子の**実際の LLM での動作**は、未検証(統合テストは、偽のモデル)。
- 子は、親と**同じ権限**で動く(サンドボックスは未実装)。ガードを破られると、親と同じ被害が出る。
- `worker` が並列に書き込むとき、**同じファイルを同時に変更**すると、壊れる。別々の worktree(`harness_worktree`。[08](08-verify-review-pr.md))を使う設計。
