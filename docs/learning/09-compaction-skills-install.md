# 09 要約・スキル・配置: 長い作業を支える周辺の仕組み

## ねらい
長い自律運転では、**会話が、モデルの文脈の上限に近づき、要約される**ことが必ず起きます。そのとき、計画や検証の結果を、失わない仕組み(要約)と、プロジェクトの初期設定を自動化する**スキル**、そして、設定を**配置するスクリプト**を理解します。

## 何を作ったか
| ファイル | 役割 |
|---|---|
| `compaction/prompt.ts`(79 行) | 要約の依頼文(日本語・5 項目)と、**確定した状態のブロック**の組み立て(純粋関数) |
| `compaction/register.ts`(74 行) | `session_before_compact` で、要約を差し替える |
| `agent/skills/nix-setup/` | スキル。`SKILL.md`、`scripts/setup.mjs`、`templates/*` |
| `scripts/install.sh` | 設定を `~/.pi/agent` に、**シンボリックリンク**で配置 |
| `agent/settings.json` | 使うモデルの一覧(`enabledModels`) |
| `lib/config.ts`、`config.default.json` | ハーネスの設定(作業ルート、保護するパス、上限など) |

## 仕組み

### A. 要約(compaction)
会話が長くなると、Pi は**古い部分を、要約に置き換えます**(compaction)。要約に、重要な情報が入らないと、**計画も、検証の結果も、忘れて**、自律運転が破綻します。

ハーネスは、`session_before_compact` で、要約を**自分で作ります**。
```
1. 要約するメッセージを、テキストにする(serializeConversation)
2. 日本語の依頼文で、モデルに要約させる(5 項目を、必ず書かせる)
     ① 変更したファイルの一覧と、検証済みか未検証か
     ② 実行した検証コマンドと結果
     ③ 作成・マージした PR
     ④ サブエージェントの担当・モデル・状態と、未解決の点
     ⑤ ユーザーが確定した決定事項と、判断待ちの事項
3. その要約に、ハーネスが持つ「確定した状態」を、そのまま付け足す
     (計画のチェックリスト、直近の検証・レビュー、PR、自分で判断したこと、サブエージェントの費用)
4. 失敗・認証なしなら、Pi の標準の要約に任せる(undefined を返す)
```
**ポイントは 3 です。** モデルが書いた要約は、**間違える・抜ける可能性**があります。計画や PR のような**正確さが要るもの**は、モデルに頼らず、**ハーネスの記録から、そのまま**書き足します。

さらに、`flow/register.ts` は、`before_agent_start` で、確定済みの計画を、**毎回システムプロンプトにも載せます**([07](07-plan-and-loop.md))。要約が、計画を取りこぼしても、**二重の保険**になります。

`config` の `compactionModel`(`provider/id`)で、**要約専用のモデル**(安いモデルなど)を指定できます。空なら、いま使っているモデル。

### B. スキル(`nix-setup`)
**スキル**は、`SKILL.md`(説明 + 手順)と、補助のスクリプトやテンプレートを、**フォルダにまとめたもの**です。Pi は、スキルの**名前と説明だけ**をモデルに見せ、**必要になったときだけ**、本文を読ませます(文脈の節約)。

`nix-setup` は、新しいプロジェクトの**最初の環境構築**を、1 回で行います。
- `flake.nix` + `.envrc`(Nix の開発環境)
- `biome.json`(lint・format)
- `.github/dependabot.yml`
- `.github/workflows/quality.yml`(CI。ジョブ名 `quality`)
- 必要なら `package.json`(`check` スクリプトつき)、`.gitignore`

`scripts/setup.mjs` は、**既存のファイルを上書きしません**(「スキップ」と表示)。`--dry-run` で、作るものを表示するだけにもできます。**決定論的な処理は、スクリプトに任せ**、`SKILL.md` は、「いつ使うか」「そのあと、何をするか」(ロックファイルのコミット、ブランチ保護)を書きます。

### C. 配置(`scripts/install.sh`)
設定を、`~/.pi/agent`(または `PI_CODING_AGENT_DIR`)に、**シンボリックリンク**で置きます。
```
extensions/harness  → <repo>/agent/extensions/harness
agents/*.md         → <repo>/agent/agents/*.md
skills/<name>       → <repo>/agent/skills/<name>
settings.json       → <repo>/agent/settings.json
```
- **リンクなので、リポジトリで編集すれば、すぐ反映**(`/reload`)
- **既存のファイルは、上書きしない**。競合は、表示して、失敗(終了コード 1)にする
- `auth.json`(API キー・トークン)には、**触れない**。リポジトリにも置かない
- 何度実行しても、同じ結果(すでに正しいリンクなら、何もしない)

### D. ハーネスの設定(`harness.json`)
`config.default.json` が既定値。`<設定ディレクトリ>/harness.json` で、**上書き**できます(`lib/config.ts`)。
| キー | 内容 |
|---|---|
| `workRoots` | 削除・書き込みを許す作業ルート(`~/Dev/kaishi` など) |
| `tempRoots` | 一時領域 |
| `protectedGlobalPaths` / `protectedHarnessPaths` | 変更を止めるパス(ubuntu-dotfiles、`~/.pi/agent`) |
| `defaultBranches` | 既定ブランチとして扱う名前 |
| `dropContextFiles` | プロジェクトの `AGENTS.md` / `CLAUDE.md` を、モデルに渡さない |
| `selectModelOnStartup` | 起動時にモデルを選ばせる |
| `compactionModel` | 要約に使うモデル |
| `subagent` | 件数・同時数・時間切れ・合計の上限 |

## なぜこう実装したか
| 選んだこと | 却下した案 | 理由 |
|---|---|---|
| **要約を、日本語の 5 項目で書かせる** | Pi の標準の要約 | 標準の要約は、**汎用**。「検証済みか」「PR」「サブエージェントの状態」といった、**このハーネスの運転に必要な項目**が、保証されない |
| **確定した状態は、モデルの要約に頼らず、そのまま付ける** | すべて、モデルに要約させる | 要約は、**抜ける・言い換える**。計画の項目の状態や、PR 番号は、**1 文字も、間違えてはいけない** |
| **失敗したら、標準の要約に戻す** | エラーで止める | 要約の失敗で、**作業全体を止めない**(`undefined` を返すと、Pi の標準の処理) |
| **要約モデルを、設定できる** | 常に同じモデル | 安いモデルで、費用を抑えたい場合がある |
| **スキルに、スクリプトを同梱** | 手順を、文章だけで書く | 毎回、**AI が手順を、少しずつ変えて、実行する**のを避ける。**決まった処理は、決まったコードで** |
| **既存ファイルを、上書きしない** | 上書き | **利用者の設定を、壊さない**。再実行しても、安全 |
| **シンボリックリンクで配置** | コピー | 編集がすぐ反映。**コピーだと、リポジトリと配置先が、ずれる** |
| **競合は、失敗にする** | 自動で、上書き・退避 | 既存の設定には、**何が入っているか分からない**。人間が、見て、判断する |
| **設定の既定を、コードの近くの JSON に** | コードに直書き | 利用者が、**コードを触らずに、上書き**できる |

## Claude Code では
| 観点 | Claude Code | このハーネス |
|---|---|---|
| 要約 | **`/compact`**(手動)と、自動の要約。**`PreCompact` フック**(標準出力が、要約への指示になる)、`PostCompact` フック(公式ドキュメントで確認) | `session_before_compact` で、**要約そのものを、差し替える** |
| 要約の制御 | 要約は、Claude Code 本体が作る。フックで**指示を足す**(`/compact` に、引数で指示も渡せる。未確認:細部) | **要約を、自分で作り**、状態を付け足す |
| 状態の保持 | `CLAUDE.md` は、要約のあとも、再読み込みされる(未確認:細部) | 計画を、毎回システムプロンプトに載せる + 要約に付ける |
| スキル | **`SKILL.md`** のフォルダ(`~/.claude/skills`、`.claude/skills`)。説明だけが、常に見え、必要なときに、本文が読まれる(未確認:細部) | `SKILL.md`(**同じ形式**。Pi も、Agent Skills の形式) |
| プラグイン | **プラグイン**で、スキル・コマンド・フック・サブエージェントを、**まとめて配布**(未確認:細部) | Pi の「パッケージ」(拡張・スキル・プロンプトを、npm や Git で配布)。このリポジトリでは、使わず、`install.sh` でリンク |
| 設定の配置 | プラグインのインストール、または、ファイルを、手で置く | `scripts/install.sh` |
| 設定の階層 | 管理者・ユーザー・プロジェクト・ローカルの 4 つ | `~/.pi/agent` と、プロジェクトの `.pi/`(信頼した場合のみ) |

**違いの要点:**
- **要約の扱い**が、いちばん違います。Claude Code は、**要約を作るのは本体**で、フックでは、**指示を足す**のが基本。Pi は、**要約そのものを、拡張が作れます**。そのぶん、**状態を、確実に残す設計**ができます。
- スキルの**形式は、ほぼ同じ**(`SKILL.md`)です。したがって、**スキルは、両方で、再利用しやすい**はずです(**未確認:** 細部の違い)。
- 配布の仕組み(プラグイン / パッケージ)は、どちらにもある。**1 人で使うなら、`install.sh` で十分**。

## 試してみよう
1. `tests/compaction.test.ts` を読み、`buildStateBlock` の出力を見る。計画のある場合・ない場合の違いは?
2. 試用環境で、`/compact` を実行する(計画が確定した状態で)。要約に、**ハーネスの記録(確定した状態)**が付くのを見る。
3. `compaction/prompt.ts` の `RETENTION_ITEMS` に、6 つ目(たとえば「未解決のエラー」)を足し、`npm test` を実行する。テストが、何を期待しているかを見る。
4. `scripts/install.sh --dry-run` を、すでに設定のある環境で実行し、**競合が、どう表示されるか**を見る。
5. 空のディレクトリで、`node agent/skills/nix-setup/scripts/setup.mjs <ディレクトリ> --dry-run` を実行し、**何が作られるか**を確認する。実行して、もう一度実行すると、**すべてスキップ**になることを確認する。
6. `harness.json` で、`defaultBranches` に `"develop"` を足し、**develop 上でも、ファイルの変更が拒否される**ことを、確かめる([03](03-guards.md))。

## 限界と注意
- **実際の LLM での、要約の質は、未検証**。依頼文が、5 項目を守らせられるかは、モデルしだい。
- 要約は、**元の会話の細部を、失う**。それを、完全に防ぐことはできない(状態ブロックは、その一部を、補う)。
- `nix-setup` は、**Nix の環境を、前提**にする。Ubuntu で、Nix を使わない場合は、`flake.nix` が不要になる(ユーザーは、Nix のバージョン管理を、好まない旨を述べている。使うかは、未決)。
- `install.sh` は、**Linux / macOS のシェル**用。Windows は、対象外。
