# Pi の導入方法: npm グローバルの懸念点

- 日付: 2026-11-13
- 状態: 暫定(ユーザーは npm グローバルでの導入を希望。懸念点を一覧にした)
- 照合した版: Pi 1.5.2 の README、docs(cli、environment-variables、packages、security)、CHANGELOG、npm レジストリ

## 前提となる事実
- Pi の最新版は **1.5.2**(2026-11-10)。公式の導入コマンドは `npm install -g --ignore-scripts @earendil-works/pi-coding-agent`。インストール時のスクリプトは不要。
- **Node.js 22.19 以上が必要。** Node 20 向けには `legacy-node20` という別の配布タグ(0.74.2 で止まっている)がある。
- 更新が非常に速い。0.81.1(2026-07-21)から 1.5.2(2026-11-10)まで約 3.5 か月で多数の版が出た。
- 更新は `pi update`(Pi 本体だけ)。更新に使うコマンドは、環境変数 `PI_SELF_UPDATE_COMMAND` または設定 `selfUpdateCommand` で差し替えられる。

## 懸念点の一覧

### A. 導入の前提
| # | 懸念 | 内容 | 対処案 |
|---|---|---|---|
| A1 | **Node のバージョン** | Ubuntu の `apt` の Node は古いことがある(Pi は 22.19 以上が必要)。`apt` の Node を使うと導入できない可能性がある | Node は home-manager(nixpkgs)の `nodejs` 、NodeSource、fnm / mise など、新しい版を入れられる経路から。Ubuntu のバージョンと、そこで入る Node の版を確認する |
| A2 | **グローバルの書き込み先** | `apt` 由来の Node では `npm install -g` が `/usr/lib` 配下に書こうとして `sudo` が必要になる。home-manager の Node は書き込み先が `/nix/store`(読み取り専用)で失敗する | 書き込める場所を `npm config set prefix ~/.npm-global`(または環境変数 `NPM_CONFIG_PREFIX`)で指定し、`~/.npm-global/bin` を PATH に足す。**この設定を dotfiles で管理する** |
| A3 | **Node のバージョン切り替え** | fnm / nvm / mise などで Node を切り替えると、Node ごとにグローバルの置き場所が変わり、Pi が見えなくなる | Node を 1 つに固定するか、A2 のように prefix を Node から独立した場所に置く |
| A4 | **Pi が要求する Node の更新** | Pi は Node 20 向けを打ち切った前例がある。将来、要求が上がると、Node を更新するまで Pi を更新できない | 更新前に CHANGELOG と `engines` を確認する |
| A5 | **導入経路の混在** | curl のインストーラ(単体のバイナリ版)と npm 版を両方入れると、どちらが動くか、どちらが更新されるか分からなくなる。単体版は一部のパッケージで追加の注意が必要(例: 単体版の Pi でサンドボックス拡張を使うには、Node 22.19 以上を PATH に置く必要がある) | npm 版 1 本に統一する |

### B. 更新と再現性
| # | 懸念 | 内容 | 対処案 |
|---|---|---|---|
| B1 | **最新版が勝手に変わる** | バージョンを指定しないと、導入するたびに版が変わる。自作の拡張は Pi の内部 API に依存するため、**更新で壊れうる**(例: 1.2.0 で `before_agent_start` の動作が変わった、1.5.0 でツール引数の検証が変わった、0.86.0 で `user_bash` の動作が変わった) | dotfiles に導入する版を書いて固定し(`@earendil-works/pi-coding-agent@1.5.2`)、意図して更新する。更新のたびに CHANGELOG の「Breaking Changes」を確認し、スモークテスト(拡張が読み込めるか、ガードが効くか)を回す |
| B2 | **古い版を避けたい要望との両立** | 固定すると、新機能や修正が入るのが遅れる。Go は新しい Pi を前提にしている | 「週に一度、更新を確認して、テストを通してから上げる」運用にする。`pi` の更新通知(`pi.dev` の版確認)は残す |
| B3 | **dotfiles の導入手順** | npm のグローバル導入は、home-manager の宣言的な管理の外になる | 導入用のスクリプト(版を指定して `npm install -g --ignore-scripts`)を dotfiles に置き、手順を 1 つに決める |

### C. 資料のルールとの衝突
| # | 懸念 | 内容 | 対処案 |
|---|---|---|---|
| C1 | **`npm install -g` の制限** | 資料では、グローバルの導入は「ユーザーが明示的に許可したときだけ」。Pi 自身の更新(`pi update`)も `npm install -g` を実行する | 更新は**ユーザーがシェルで手動で行う**(Pi の外で実行する)ことで、エージェントには許可しないルールをそのまま保てる。エージェントが `pi update` を実行しないようにガードに足す |
| C2 | **`sudo` を使わせない** | A2 を放置すると、導入や更新に `sudo` が要る状況になる | A2 のとおり、ユーザー領域の prefix にして、`sudo` を不要にする |
| C3 | **グローバル環境(home-manager)を開発中に変えさせない** | 導入場所が `~/.npm-global` なら、home-manager の管理の外にあり、かつ開発中の変更は拒否できる | `~/.npm-global` への書き込みを、ガードの対象に含める |

### D. 拡張・パッケージの安全性
| # | 懸念 | 内容 | 対処案 |
|---|---|---|---|
| D1 | **サプライチェーン** | `pi install npm:...` で入れる拡張は、**全権限で動き、`auth.json`(API キーと OAuth トークン)にも触れる**(Codex の使用率を出す拡張は、実際にトークンを読む)。公式ドキュメントも、導入前のソース確認を求めている | 導入前にソースを読む。`@x.y.z` で版を固定する(`pi install npm:@foo/pi-tools@1.2.3`)。固定した版は `pi update` で更新されない。導入元は少数に絞る |
| D2 | **`--ignore-scripts`** | Pi 本体の導入では、依存先のインストール時スクリプトを無効にするのが公式の推奨 | 公式のコマンドのとおり付ける |
| D3 | **拡張の置き場所** | `pi install` した拡張は `~/.pi/agent/npm/`(グローバル npm とは別)に入る | dotfiles の管理対象にするか、導入コマンドを記録して再現する |
| D4 | **プロジェクト内の `.pi/`** | リポジトリ内の拡張や設定は、信頼した場合だけ読み込まれる(プロジェクトの信頼の仕組み) | `defaultProjectTrust` の設定を決める(既定は `ask`) |

### E. 運用面
| # | 懸念 | 内容 | 対処案 |
|---|---|---|---|
| E1 | **SSH 経由での PATH** | MacBook から SSH で入ったときに、PATH に `~/.npm-global/bin` が入っていないと `pi` が見つからない | PATH の設定は、対話用でないログインシェルでも読まれる場所に書く(例: `~/.profile`)。tmux 内のシェルでも確認する |
| E2 | **サブエージェントの起動** | 公式サンプルの子プロセスは、`process.execPath` と `process.argv[1]`、または PATH 上の `pi` で自分自身を起動する | PATH を保つ。子に渡す環境変数が PATH を壊さないようにする |
| E3 | **テレメトリと版確認** | `pi.dev` への版確認と、導入・更新時の匿名の通知が既定で有効 | 必要なら `PI_TELEMETRY=0`、`PI_SKIP_VERSION_CHECK=1`。ただし後者は更新通知が出なくなるので、「最新を使いたい」方針と衝突する。通知は残し、テレメトリだけ切るのが妥当 |
| E4 | **認証情報** | `~/.pi/agent/auth.json` に API キーと OAuth トークンが入る | dotfiles に含めない。権限を 600 にする。キーを環境変数や秘密管理コマンド(`auth.json` で `!コマンド` 形式)で渡す方法もある |
| E5 | **サンドボックスとの関係** | サンドボックスは、`~/.npm-global` と `~/.pi/agent` への書き込みを禁止する設定にすべき(拡張が自分の設定や自分自身を書き換えられないように) | サンドボックスの設定で書き込み拒否に入れる(`erichll/pi-sandbox` は Pi の設定とインストール先を既定で書き込み禁止にする) |

## まとめ
- **npm グローバルでの導入は妥当。** ただし、**A2(ユーザー領域の prefix)と B1(版の固定と意図した更新)が実質の条件**になる。
- 最も効くのは次の 3 つ。
  1. `~/.npm-global` を prefix にする(A2)。`sudo` と `/nix/store` の問題が両方消える。
  2. 版を固定し、更新はユーザーが手動で行う(B1、C1)。自作の拡張が Pi の更新で壊れるのを防ぐ。
  3. 拡張は導入前にソースを読み、版を固定する(D1)。
- 資料の「古い版を使いたくない」と、B1 の「版の固定」は引っ張り合う。**「固定するが、週次で最新を確認して上げる」運用が落としどころ**。
