# Pi coding agent ハーネス設計（Ubuntu PC）

> 出典: ユーザーが 2026-11-13 に提示した資料(原文のまま保存)。評価結果は `../feasibility-assessment.md`。

## 概要
- Ubuntu PC で、Pi coding agent を使ってハーネスを一から自作する
- 設定は katoline/ubuntu-dotfiles で管理する

## 基本方針：ルールは「コンテキスト」ではなく「ハーネス」で管理する
- 作業のルールは、AI に読ませる AGENTS.md（コンテキスト）には書かない
- Pi の拡張・フック・コマンド・スクリプト・設定として作り込み、仕組みで守らせる
- 理由：コンテキストに書いたルールは、守られるかどうかが毎回ぶれる（非決定論）。ハーネスで強制すれば毎回同じ動きになる（決定論）
- ルールは次の3種類に分けて実装する
  1. 仕組みで止める・強制するもの
  2. 流れとして組み込むもの
  3. 固定の指示として渡すもの（判断が要るもの。AGENTS.md には頼らず、ハーネスの中から渡す）

## プロバイダー（3種類）
| プロバイダー | 使い方 |
|---|---|
| OpenCode Go（サブスク） | サブエージェントの既定。メインとしても選べる |
| Anthropic API | API キーを直接読み込ませて使う（Claude Code のサブスクは Pi で使えないため） |
| Codex | メインとして選べる |

- API キーはリポジトリに置かない（環境変数などで別に管理する）
- Anthropic API の利用額の上限などは、Anthropic Console の画面で設定・確認する

## 利用状況の表示
| プロバイダー | 表示するもの |
|---|---|
| Anthropic API | 残りのクレジット（Anthropic Console で見ている残りクレジットと同じもの） |
| OpenCode Go | 5時間・週間・月間の制限を、それぞれ何%使っているか |
| Codex | 5時間・週間の制限を、それぞれ何%使っているか |

## メインエージェント
- 固定しない
- 起動時に `/models` で選んだモデルを、そのセッションのメインエージェントにする

### `/models` コマンド
- OpenCode Go：サブスクで使えるモデル一覧
- Anthropic API：Opus 5.5／Sonnet 5.5／Fable 5.2／Haiku 5.5
- Codex：使えるモデル一覧

## サブエージェント
- 既定は OpenCode（OpenCode Go の DeepSeek V4.1 Flash）
- `/subagent-model`（仮）で、好きなモデルに切り替えられる
- 比較的単純な作業は、サブエージェントを使わずメインエージェントだけでやる
- サブエージェントを使うかどうかは自動で判断する

## 開発の流れ
1. 起動時に `/models` でメインのモデルを選ぶ
2. Plan：要件と判断をすべてユーザーと確認し、確定させる
3. Do：単純な作業はメインだけで進め、重い作業・並行できる作業はサブエージェントに任せる
4. Check：検証とレビューを行う
5. Act：直して再チェックする
6. PR を作り、CI が通ったら main へ自動マージする

## スキル：Nix セットアップ（1つのスキルにまとめる）
プロジェクトの最初の環境構築で起動すると、次がそろう。
1. Nix で環境を作る
2. Biome を設定する（lint・format）
3. Dependabot の設定ファイル（YAML）を作る
4. CI チェック（テストなど）の GitHub Actions ワークフロー（YAML）を作る

# ハーネスで実装するルール（仕様）

## 1. 仕組みで止める・強制するもの

### Git 操作
- 既定ブランチ（`main` / `master` / `origin/HEAD` の指す先）への直接の commit・push を拒否する（マージは必ず PR 経由）
- 既定ブランチ上で作業を始めたら、先に作業ブランチを作らせる
- force push・`--no-verify`・マージ済み以外のリモートブランチの削除を拒否する
- テスト・CI が通っていない PR、未検証の変更のマージを拒否する
- commit・push・PR・マージは、メインセッションからだけ許可する（サブエージェント・委譲先からは拒否する）
- 作業ツリー・履歴・リモートを壊す操作（reset --hard / clean / 変更の破棄 / branch -D / stash drop / rebase / amend）は、ユーザーが明示的に許可したときだけ通す

### ファイル削除・プロセス停止
- 削除できるのは、作業ルート（`~/Dev/kaishi`・`~/Dev/seino914`・`~/Dev/hobby`・`~/orca/workspaces`）と一時領域（`$TMPDIR`・`/tmp/claude-*`）の内側だけにする
- 削除の対象に、変数やコマンド置換で組み立てたパスや、`cd` と組み合わせた削除を使わせない（具体的なパスだけ許可する）
- `pkill` / `killall` を拒否する。停止は `kill $(lsof -ti :<ポート>)` か PID 指定の `kill` だけにする

### パッケージインストール（Nix 運用）
- グローバル環境（`~/Dev/kaishi/ubuntu-dotfiles` の home-manager）を開発中に変えさせない
- プロジェクトの外に恒久的な影響が出るインストール（`apt` / `snap` / `npm install -g` / `pip install --user` / `nix profile install` / `nix-env -i` 等）と `home-manager switch` は、ユーザーが明示的に許可したときだけ通す
- `sudo` は実行させない（必要なときはコマンドを示してユーザーに依頼する）
- lock ファイルで管理しているプロジェクト内の依存（`npm install`・`pnpm add` 等）は通常どおり許可する

### 秘密情報
- `.env`・秘密鍵・トークン・API キーの読み取り・出力・コミットを拒否する
- 設定例は `.env.example` 等のテンプレートを使う

### 出力・表示
- 作業が完了したら、最終応答の最後の1行を必ず「🚀作業が完了しました！」にする
- サブエージェントの起動時に「⏳ サブエージェント（<モデル>）で<作業内容>を実行中」、終了時に「✅ <作業内容>が完了」を表示する
- サブエージェントの既定モデルを OpenCode Go の DeepSeek V4.1 Flash に固定する（`/subagent-model` で変更されたときだけ変える）

## 2. 流れとして組み込むもの

### 自律実行
- 判断が必要なこと（完了条件・判断の基準・迷ったときの扱い・細かい仕様の選択）は、Plan の段階ですべてユーザーと確認する
- プランが確定したら、ユーザーに質問せずに完了まで進める
- プランで決めていない判断が出たら、プランの方針に沿う妥当な既定で進め、完了報告に「自分で判断したこと」として書く
- ユーザーにしかできないこと（`sudo`・秘密情報の用意・破壊的な操作の許可など）は、その項目だけ保留にして他の項目を進め、最後にまとめて依頼する

### PDCA のループ（ファイルを変更する作業）
- **Plan**：依頼を完了条件つきの要件に分解してチェックリストにする。付随作業（検証・独立レビュー・記録や README・PR・マージ）も項目に入れる
- **Do**：1項目ずつ進め、終わるたびにチェックリストを更新する。見つけた追加作業はリストに足す
- **Check**：検証コマンドを通したうえで、差分を要件と1項目ずつ突き合わせ、満たした根拠（`file:line`・コマンドの出力）を挙げる。挙動に関わる変更は独立レビューを受ける
- **Act**：失敗・未達・採用したレビュー指摘を直し、直した差分に対して Check をやり直す。3周で収まらない項目は、止まらずに未完了として残して他の項目を進め、最後に報告する
- 完了報告には、要件ごとの「完了 / 未完了（理由）」、実行した検証・レビューの結果、作成・マージした PR を書く。根拠を示せない項目は完了と書かない

### 検証
- プロジェクトの検証コマンド（lint・型チェック・テスト・ビルド等）を変更のあとに必ず実行する。無ければ「未検証」と報告し、自動マージはしない
- 落ちたら直す。自分の変更と関係ない既存の失敗は報告だけにする
- テストの skip・削除・期待値の書き換え、lint / 型チェックのルール無効化・除外追加で「通す」ことは禁止する

### PR・マージ
- コミットと PR は細かく分ける（1つの PR に1つの目的）
- PR 本文は、差分とコミットから「概要・変更点・確認方法」の固定の形で自動生成する（既存の PR があれば作り直して更新）
- テスト・CI がすべて通ったら、ユーザーの確認なしで main へマージする。落ちたら直してから CI を通し直す
- 複数のタスクは、タスクごとに PR を作り、CI が通ったものから順にマージする。最後に、作成・マージした PR を一覧で報告する

### 独立レビュー
- 挙動に関わる変更（ドキュメントのみ・数行の自明な修正は除く）は、完了の前に、新しいコンテキストのレビュー用サブエージェントへ差分と要件だけを渡してレビューさせる
- 採否はメインエージェントが判断する
- 修正後の再レビューは、直した差分だけを対象にする

### 作業用 worktree
- タスク用の worktree があれば使い回し、無ければメインセッションが作る。他セッションの worktree とブランチは削除しない
- 完了後、成果物がコミット済みか移送済みで、未保存のものが無いことを確認したら、メインセッションがメイン checkout から絶対パスを指定した `git worktree remove <絶対パス>`（`--force` なし）で削除する
- 未保存の成果物が残る・削除に失敗する場合は残して、理由とパスを報告する（`--force` で再試行しない）

### 要約（compact）のときに残すもの
- 変更したファイルの一覧と、検証済みか未検証か
- 実行した検証コマンドと結果（失敗ならその内容）
- 作成・マージした PR
- サブエージェントの担当・モデル・状態と、未解決の点
- ユーザーが確定した決定事項と、判断待ちの事項

## 3. 固定の指示として渡すもの（判断が要るもの）

### 言語
- 応答・説明・コード内のコメントは日本語（サブエージェントも同じ）
- 成果物（README・コミットメッセージ等）の言語は、プロジェクトの既存ドキュメントに合わせる（無ければ日本語）
- コマンド・設定キー・パス・モデル ID は原文のまま

### サブエージェントへの任せ方
- メインエージェントは、要件整理・設計・分解・指示・レビュー・最終判断を担う
- 1〜2ファイルの確認・自明な局所修正・設計と切り離せない難所は、メインだけでやる。実装や複数ファイルにまたがる調査はサブエージェントに任せる
- 指示は自己完結させる（対象ファイル・設計方針・制約・完了条件）。独立したタスクは並列に起動する
- 分かっている事実は渡して、再調査させない。調べものは問いを具体的に挙げ、確認できないものは「確認できず」と報告させる
- 報告は「変更ファイル／実行した検証と結果／未解決点」の形で受け取り、メインがレビューしてから完了にする
- サブエージェントとして起動されたら、独立レビュー・commit・PR・マージは親に任せ、検証と要件ごとの報告までを行う

### レビューの範囲
- **外部の入力・利用者に晒される部品**（API・Web 画面・認証認可・外部データの処理・外部入力から組み立てるシェル / SQL / パス・秘密情報・権限境界）は、攻撃者がいる前提で見る
- **自分たちだけが操作する部品**（CLI のフック・開発用スクリプト・ヒューリスティックな検査）は、普通の使い方で起きる事故だけを見る
- 指摘ごとに、再現経路を1文で書く。書けないものは出さない
- 指摘しないもの：現実に来ない規模の入力での性能、好みの問題、ドキュメントで「対象外」「既知の制約」とされているもの
- 直す側は「直す / 対象外」に分け、対象外には理由を一言添える
- 同じ部品に同じ種類の指摘が2回続いたら、パッチを重ねずに設計の見直し（セキュリティなら許可リスト型の検証やフレームワーク任せ、事故防止なら対象外の明文化や単純化）を完了報告で提案する
