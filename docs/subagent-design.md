# サブエージェント設計: 公式サンプルの仕組みと改造プラン

- 日付: 2026-11-13
- 状態: 保留(ユーザーが A〜C の決定を保留。方式 A を暫定の前提として進める)
- 照合した版: Pi 1.5.2(最新)のサンプル `examples/extensions/subagent/`。0.81.1 版との差分も確認済み
- 注意: ソースとドキュメントの読み込みによる評価。実機では動かしていない

## 1. Pi にサブエージェントは標準で付いていない
Pi の README に「サブエージェントとプランモードは付属しない。欲しければ拡張で作るか、パッケージを入れる」とあります(設計思想)。公式サンプルは「そのやり方の一例」で、Claude Code の Agent(旧 Task)ツールに似せて作られています。

## 2. 公式サンプルの動き方

### 構成
```
subagent/
├── index.ts        拡張の本体。`subagent` というツールを登録する
├── agents.ts       エージェント定義(.md)の探索と読み込み
├── agents/*.md     scout(調査)/ planner(計画)/ reviewer(レビュー)/ worker(実装)
└── prompts/*.md    ワークフロー用のプロンプトテンプレート(/implement など)
```

### 流れ
1. メインのモデルが `subagent` ツールを呼ぶ(モデルが自分で判断して呼ぶ。拡張が自動で呼ぶわけではない)。
2. 拡張が、エージェント定義(`~/.pi/agent/agents/*.md`)を読む。形式は Claude Code と同じ「YAML の先頭部 + 本文」で、`name`、`description`、`tools`、`model` を書く。本文がシステムプロンプトになる。
3. **子プロセスとして `pi` を丸ごと起動する。** 起動コマンドは次の形(1.5.2 版も同じ)。
   ```
   pi --mode json -p --no-session [--model <モデル>] [--tools <許可ツール>] \
      --append-system-prompt <一時ファイル> "Task: <依頼>"
   ```
   - `-p` は「1 回だけ実行して終了する」モード(対話 UI なし)
   - `--mode json` は進捗を JSON の 1 行ずつで標準出力に流すモード
   - `--no-session` は会話を保存しない
   - 標準入力は閉じる(`stdio: ["ignore", ...]`)。子は**ユーザーに質問できない**
4. 親は、子の JSON を読みながら、ツール呼び出しやトークン数・費用をリアルタイムで画面に出す(⏳ 実行中 / ✓ 完了 / ✗ 失敗)。
5. 子が終わると、**最後のアシスタントの返答だけ**を親のツール結果として返す(上限 50KB)。子の途中経過は親のコンテキストに入らない。
6. 中止(Ctrl+C)は子に SIGTERM を送り、5 秒後に SIGKILL する。

### 3 つの実行モード
| モード | 指定 | 動き |
|---|---|---|
| 単発 | `{ agent, task }` | 1 つのエージェントに 1 つの依頼 |
| 並列 | `{ tasks: [...] }` | 最大 8 件を登録し、同時に動くのは 4 件まで |
| 連鎖 | `{ chain: [...] }` | 前の出力を `{previous}` で次に渡す。失敗した時点で止まる |

### 付随する仕組み
- **ツールの制限:** `tools:` に書いた組み込みツールだけを子に許可する(`--tools`)。
- **モデルの決め方:** 1.5.2 版では、エージェント定義に `model:` があればそれを使い、**無ければ親が今使っているモデルと思考レベルを引き継ぐ**(0.81.1 版は無ければ未指定)。
- **プロジェクトローカルのエージェント:** 既定では `~/.pi/agent/agents/` だけを読む。リポジトリ内の `.pi/agents/` は、確認ダイアログを出したうえでだけ使う(リポジトリ由来のプロンプトは信頼できないため)。
- **作業ディレクトリ:** 呼び出しごとに `cwd` を指定できる。

### サンプルで「やっていないこと」(改造が必要な点)
| やっていないこと | 影響 |
|---|---|
| 子に環境変数を足さない(親の環境をそのまま渡す) | 子が「サブエージェントである」ことを拡張側から判別できない。資料の「commit・push・PR・マージはメインだけ」を実現するには追加が要る |
| 子の拡張を無効にしていない(`--no-extensions` なし) | 子でも `~/.pi/agent/extensions/` の拡張が自動で読み込まれる。**ガード拡張は子にも効く**(利点)。一方、`subagent` ツール自体も子に読み込まれうる(`tools:` 未指定の worker は再帰呼び出しが可能。要確認) |
| AGENTS.md の読み込みを止めていない(`-nc` なし) | 子もプロジェクトの AGENTS.md を読む |
| 親の費用に子の費用を足さない | 親のフッターの費用は親のセッション分だけ。子の費用は各子の結果にだけ出る |
| 並列の書き込み衝突を防がない | 同じチェックアウトで複数の worker が編集すると衝突する。`cwd` で別の worktree を指す運用が必要 |
| レビュー担当の「読み取り専用」は文章の指示だけ | reviewer の定義に「bash は読み取りだけ。ツール権限は完全には強制できない前提で」とある。強制ではない |
| 報告の形式を強制しない | 「変更ファイル/検証と結果/未解決点」は指示でしか縛れない |

## 3. 通常のサブエージェント(Claude Code など)との違い
Claude Code の説明は検索結果による(公式ドキュメントでの再確認はしていない)。OpenCode については確認できなかった。

| 観点 | Claude Code の Agent(旧 Task)ツール | Pi の公式サンプル |
|---|---|---|
| 実装の位置 | 本体の機能 | 拡張(自作・改造可能) |
| 起動単位 | 本体が管理するサブエージェント(独立したコンテキストウィンドウ) | **別の OS プロセス**として `pi` を起動 |
| 定義 | `.md` の先頭部(name、description、tools、model など)+ 本文 | ほぼ同じ形式(サンプルが似せている) |
| 結果 | 要約だけが親に返る | 最後の返答だけが親に返る |
| 入れ子 | サブエージェントがさらにサブエージェントを呼ぶのは不可 | 既定では防いでいない(自分で防ぐ) |
| ユーザーへの質問 | 親経由 | 子は質問できない(`-p` で UI なし) |
| 権限 | 親の権限を継承したうえでツールを制限 | 子は独立した `pi` プロセス。**子の拡張は自分で読み込む**ので、ガードは拡張で効かせる |
| フックの効き方 | 不明(要確認) | 子の拡張が自分で `tool_call` を処理する |

## 4. 方式の候補

### 方式 A: 公式サンプルを改造する(別プロセス方式)
- 子 = 独立した `pi` プロセス。OS の境界があるので、**子だけをサンドボックスや別ユーザーで包みやすい**。環境変数を子に渡せば、モデルが書き換えられない形で「子である」と伝えられる。
- 自分のコードなので、資料の仕様(表示文言、既定モデル、報告形式)をそのまま実装できる。
- 欠点: 約 1,000 行のサンプルを自分で保守する。Pi の更新で壊れうる(Pi は更新が速い)。バックグラウンド実行、再起動復帰などは自作になる。

### 方式 B: コミュニティのパッケージ `pi-subagents` を使う
[pi-subagents](https://pi.dev/packages/pi-subagents)(v0.88.1、MIT、月間約 93 万ダウンロード、Pi 1.2.0 以上が必要)。
- 前景の子は**親の Pi プロセスの内部**でセッションとして動く。背景実行は別の常駐プロセス。並列、連鎖、保存できるワークフロー、worktree 隔離、役割ごとのモデル指定、再帰の防止(`maxSubagentSpawnsPerRun` など)、進捗画面(`/subagents-fleet`)がある。
- 欠点: 機能が多く、**資料の仕様(コミットはメインだけ、固定の表示文言、既定モデル)に合わせる余地は設定と拡張 API の範囲に限られる**。内部実行なので、親の `tool_call` ガードが子のツール呼び出しにも効くかは**未確認**(サンプルの別プロセス方式とは性質が違う)。更新が非常に速く、依存先が増える。
- パッケージは全権限で動く。導入前にソースの確認と、版の固定が必要。

### 方式 C: SDK で内部実行する子を自作する
Pi の SDK(`createAgentSession`)で、親プロセスの中に子セッションを作る。起動が速く、状態を共有できる。ただし OS の境界がなく、プロセス単位のサンドボックスは使えない。方式 B の自作版にあたるため、現時点では推奨しない。

### 比較
| 観点 | A: サンプル改造 | B: pi-subagents | C: SDK 自作 |
|---|---|---|---|
| 資料の仕様への合わせやすさ | ◎ 全部自分で決められる | △ 設定と拡張 API の範囲 | ◎ |
| 「コミットはメインだけ」の確実さ | ◎ 環境変数 + 子の拡張で止められる | △ 要検証 | ○ 要設計 |
| 子単位のサンドボックス | ◎ プロセス単位で包める | △ 提供元の連携機能に依存(erichll/pi-sandbox が対応を謳う) | ✗ |
| 機能の多さ(背景、worktree 隔離、進捗) | △ 自作が必要 | ◎ | △ |
| 保守の手間 | △ 自分で追従 | ○ 提供元が追従(ただし更新が速い) | △ |
| 初期の実装量 | ○ サンプルが土台 | ◎ 入れるだけ | △ |

### 暫定の推奨(ユーザーが決める)
**まず方式 A で最小構成を作る。** 資料の要件の中心が「決定論的に止める」ことで、プロセス境界がその土台になるため。方式 B は、「親の `tool_call` ガードが子に効くか」「資料の表示・既定モデルに合わせられるか」を試験用に確かめ、背景実行や worktree 隔離が本当に必要になった時点で再検討する。

## 5. 方式 A の改造プラン
優先度の高い順。各項目は Pi の既存の仕組みで実現できる。

### 必須(資料の仕様を満たすために必要)
1. **子に環境変数を渡す。** `spawn` の `env` に `PI_SUBAGENT=1`、`PI_SUBAGENT_ROLE=<役割>`、親のセッション ID を足す。Pi 自体も、子が自分を判別できるよう `PI_CODING_AGENT=true` と `PI_SESSION_ID` 等を渡している(1.5.2)。
2. **子専用のガード。** 同じ拡張の中で、環境変数があれば `tool_call` を次のように処理する。
   - `git commit` / `git push` / `gh pr ...` / マージ系を、**確認なしで拒否**(`-p` では UI がなく確認ダイアログを出せない。サンプル `permission-gate.ts` と同じく、UI がなければ拒否にする実装にする)
   - `subagent` ツール自体を子から呼べなくする(再帰の防止)
3. **既定モデルの固定。** エージェント定義に `model: opencode-go/deepseek-v4.1-flash` を書く。1.5.2 のサンプルは「モデルの指定が無ければ親のモデルを引き継ぐ」ので、**固定したいなら必ず定義に書く**(引き継ぎを使いたい役割は書かない)。`/subagent-model` は、選択を `pi.appendEntry()` で保存し、起動時に定義より優先して `--model` に渡す形で実装する。
4. **表示文言の差し替え。** 開始時「⏳ サブエージェント(<モデル>)で<作業内容>を実行中」と、終了時「✅ <作業内容>が完了」を、ツールの描画(`renderCall` / `renderResult`)と `ctx.ui.setWidget` で出す。`<作業内容>` は、依頼に短い題名の引数(例: `title`)を必須で持たせて取る。
5. **子の AGENTS.md を読まない。** 子の起動引数に `-nc`(`--no-context-files`)を足し、役割ごとの指示は `--append-system-prompt` で渡す(資料の「AGENTS.md に頼らず、ハーネスの中から渡す」と一致)。

### 推奨(安全性と運用のため)
6. **費用の合算。** 子の費用(既にサンプルが集計している)を、親のステータスに加算して表示し、`appendEntry` で保存する。Anthropic API をサブエージェントでも使う場合の「そのセッションで使った額」を正しく出すために必要。
7. **報告の形式の強制。** 公式サンプル `structured-output.ts`(終了と同時に構造化された結果を返す専用ツール)を子に持たせ、「変更ファイル/実行した検証と結果/未解決点」を必須の項目にする。文章の指示だけに頼るより決定論に近づく。
8. **並列の書き込みの分離。** 書き込みをするエージェント(worker)を並列に動かすときは、1 件ごとに別の git worktree を作り、`cwd` で渡す。読み取り専用(scout、reviewer)は同じ場所でよい。同時実行数は、Go の 5 時間・週間の上限を考えて 4 より小さくしてもよい。
9. **読み取り専用役の強制。** reviewer / scout は、`tools:` から `bash` を外す(例: read、grep、find、ls だけ)。`git diff` が必要な場合は、親が差分をファイルにして渡す(子の bash を許可しない)。サンプルの reviewer は bash を許可し、文章で縛っているだけ。
10. **子のログ保存。** `--no-session` の代わりに専用のログディレクトリへ JSON イベントを残す(後でレビューや不具合の調査に使える)。

### 任意
11. **子単位のサンドボックス。** 起動コマンドを `bwrap ... pi ...` のように包む、または子が読み込むサンドボックス拡張を使う(`sandbox-options.md` 参照)。
12. **子専用の設定ディレクトリ。** `PI_CODING_AGENT_DIR` で子の設定ディレクトリを別にでき、子には最小限の拡張だけ読ませられる(認証は `auth.json` のシンボリックリンクなどで共有する必要がある)。
13. **「使うかどうか」の自動判断。** 資料でも未決。決定論にするなら、拡張が「対象ファイル数、変更の種類」などのルールで `subagent` ツールを有効・無効にする(`pi.setActiveTools()`)。モデルの判断に任せるなら、ツールの説明文で基準を書く。

## 6. 方式を決めるために、ユーザーに決めてほしいこと
1. 方式 A(サンプル改造)から始めてよいか。方式 B を試験導入して比較するか。
2. 並列の書き込み(worktree を分ける運用)を、最初から入れるか、後回しにするか。
3. 子をサンドボックスで包むのは、最初からか、後からか(`sandbox-options.md` の結論に依存する)。
4. 「サブエージェントを使うかの判断」を、ルールで縛るか、モデルの判断に任せるか。
