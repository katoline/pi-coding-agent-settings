# サンドボックスの 2 つの候補: Gondolin と、bubblewrap 系(@erichll/pi-sandbox)

- 日付: 2026-11-13
- 出典: Gondolin の [README](https://github.com/earendil-works/gondolin)、`@erichll/pi-sandbox` の README、Pi 1.5.2 の公式ドキュメントとサンプル(`examples/extensions/gondolin/`)。**実機では動かしていない**
- 関連: [sandbox-options.md](sandbox-options.md)(選択肢の一覧)、[research/sandbox-practices.md](research/sandbox-practices.md)(実践例)

## 0. サンドボックスは、何のためにあるか
AI が実行するコマンドを、**「見える範囲・触れる範囲・通信できる先」が決まった箱の中**で動かす仕組みです。箱の壁を作るのは、コマンドの文字列を検査するガード(今のハーネス)ではなく、OS や VM です。そのため、`python -c` や `sh -c` のような回りくどい書き方でも、壁は越えられません。

今のハーネスのガードは、日常の事故を止める役で、壁の代わりにはなりません。サンドボックスが入ると、**「壁の内側なら確認なしで自由に作業させる」**ことができ、止まる回数が減ります(自律ループと相性が良い)。

## 1. 候補 A: Gondolin(Pi 公式のマイクロ VM)

### 何か
**Pi の道具だけを、小さな別のコンピュータ(Linux のマイクロ VM)の中で動かす**仕組みです。Pi 本体(画面、モデルとのやり取り、拡張)は、いつものとおりホストで動き、`bash`・`read`・`write`・`edit`・`grep`・`find`・`ls` の実行だけが VM の中に流れます。

### 仕組み
- **VM:** Linux x86_64 で `/dev/kvm` が使えれば、`libkrun`(軽量な VM)で動き、QEMU は不要。使えなければ QEMU に切り替わる。Node 22.19 以上。
- **ファイル:** プロジェクトのディレクトリだけが、VM の中の `/workspace` として見える(書き込みはホストに反映される)。ホストの `~/.ssh`、`~/.aws`、ホームの他の場所は、**そもそも見えない**。
- **VM の中身(ゲスト):** Alpine Linux(musl)の最小のイメージ(約 200MB、初回にダウンロード)。`git` は自分で追加する。`gondolin build` で、パッケージを足した独自のイメージを作れる。
- **通信:** ホスト側のプログラムが、HTTP/TLS の宛先を許可リストで制御できる。API キーは、VM には**ダミーの値だけ**を渡し、許可した宛先に出るときだけ、ホストが本物に置き換える(キーが VM の中に入らない)。
- **実行:** `vm.exec` で、VM の中の `/bin/sh -lc` で実行する。

### 良い点
- **隔離が強い。** ホストのカーネルとは別なので、ファイルも、ほかのプロセスも、ホームの秘密も、見えない。
- Pi の公式(`examples/extensions/gondolin/`)なので、Pi の更新に追従しやすい。
- キーを VM に入れない仕組みがある(正しく設定すれば)。

### 気をつける点(今の私たちの環境に直結するもの)
1. **ホストの道具が使えない。** VM の中は別の Alpine なので、**ホストの Nix、`node`、`biome`、`gh` はそのままでは使えない**。プロジェクトの検証コマンド(`harness_verify`)も、VM の中で動く(`bash` が VM に差し替わるため)。Nix の環境を使う運用だと、**VM のイメージに、必要な道具を入れ直す**必要がある。Gondolin で Nix を使った公開例は、見つからなかった。
2. **「実験的」と明記**されている。更新が速く、仕様が変わりうる。
3. **公式のサンプルは、設定が最小限**(PoC)。サンプルのままだと、**VM からの通信は制限されず、ホストの環境変数(API キーなど)が VM の中に引き継がれる**(公式ドキュメントの表にも明記)。安全にするには、許可リストとキーの渡し方を、自分で設定する必要がある。
4. 作業ディレクトリは、VM から**書き込める**。`.git/hooks` を書き換えられると、あとでホストで `git` を実行したときに動く(公式のサンプルには、これを防ぐ仕組みがない)。
5. **サブエージェントは自動では隔離されない。** 私たちのサブエージェントは、ホストが別プロセスで起動する(`pi` の子プロセス)。Gondolin が囲うのは、ホストの Pi のツールだけなので、**子の `bash` は、そのままではホストで動く**。子にも Gondolin を読み込ませると、子ごとに VM が立つ(重い)。
6. `git push` が遅いという既知の問題(Issue #162)、Pi のセッション変数が VM に渡らない問題(#205)がある。

## 2. 候補 B: bubblewrap 系(@erichll/pi-sandbox)

### 何か
**同じ PC の中で、コマンドごとに「見える範囲を絞った箱」を作って、その中で動かす**仕組みです。VM ではなく、Linux のカーネルの機能(名前空間)で、見える範囲を絞ります。Claude Code が使っているのと同じ部品(Anthropic の `sandbox-runtime`、Linux では `bubblewrap`)の上に作られた、コミュニティ製の Pi 拡張です。

### 仕組み
- **ファイル:** `bubblewrap`(`bwrap`)が、コマンドごとに、ファイルシステムの見え方を作り直す。**ホストの道具(Nix の `/nix`、`node`、`biome` など)は、読み取り専用で、そのまま見える。** 書き込めるのは、作業ディレクトリと、コマンドごとの専用の一時ディレクトリだけ。
- **読み取りも制限する(fail closed)。** 許可した場所の外は、**読めない**(`~/.ssh`、`~/.aws` など)。必要な場所は、設定の `filesystem.additionalAllowRead` で足す。
- **書き込みの保護:** Pi の設定、拡張のディレクトリ、Git のフック、`.env`・`*.pem`・`*.key` などは、作業ディレクトリの中でも、書き込み禁止。
- **通信:** プロキシを通し、許可リスト(`allowedDomains`)と拒否リスト(`deniedDomains`)で制御する。許可リストにない宛先は、(1)人またはレビュー用モデル(`pi-auto-review`)に 1 回ごとに確認する、か、(2)**厳格モード(`strictAllowlist: true`)で、確認なしで拒否**する。無人で動かすなら、厳格モード。
- **サブエージェント:** 拡張自身の `subagent` ツール(ワーカーのプロセスの木ごとに隔離。同時 4、深さ 3)で守る。

### 良い点
- **Nix とホストの道具が、そのまま使える。** 検証コマンドも、ふだんどおり動く(壁の内側で)。
- **読み取りもネットワークも閉じられる。** 厳格モードなら、確認なしで拒否するので、**自律ループが止まらない**。
- Claude Code と同じ部品で、事例が多い。更新が活発(2026-11-03 に 0.29.2)。

### 気をつける点
1. **VM ほどは強くない。** ホストのカーネルを共有する。ホストの道具を読み取りで見せる分、見せ方の設計が要る。
2. **Ubuntu のバージョンに依存する設定が、`sudo` で要る(あなたが 1 回行う)。**
   - 共通: `sudo apt-get install bubblewrap socat ripgrep`
   - **Ubuntu 24.04 以降:** AppArmor が、一般ユーザーの名前空間を制限するため、`sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`(再起動後も有効にするには、設定ファイルへ)が必要。
   - **Ubuntu 26.04:** それでも、`bwrap-userns-restrict` というプロファイルが全権限を拒否するため、`sudo apparmor_parser -R /etc/apparmor.d/bwrap-userns-restrict` で、**このプロファイルを外さない限り、起動しない**。
   - Ubuntu のバージョンを、まず確認する必要がある(下の確認コマンド)。
3. **`sandbox-runtime` は「研究プレビュー」。**
4. **ファイルツール(`read`・`write`・`edit`)も包まれるかは、README に記載がなく、確認できず。** 包まれない場合は、私たちのガード(パスの検査)が担当する(すでに実装済み)。
5. **許可した宛先は、情報の持ち出しの経路になりうる。** `github.com` のような広い宛先を許可すると、そこに送れる(README も明記)。
6. 拡張自身が **`subagent` ツールを持つ**ため、私たちの `subagent` と**名前が衝突する**。使い分けか、どちらかに寄せる必要がある。私たちの子プロセスに、この拡張を読み込ませないと、**子の `bash` は箱の外**になる。
7. 依存が多い(`pi-auto-review` など)。設定の変更は、Pi の再読み込みが必要。

## 3. 比較

| 観点 | A: Gondolin(マイクロ VM) | B: bubblewrap 系(erichll) |
|---|---|---|
| 隔離の強さ | **強い**(別のカーネル) | 中(カーネル共有) |
| Nix・ホストの道具 | **使えない**(ゲストに入れ直す) | **そのまま使える** |
| 読み取りの制限 | 見えない(プロジェクトだけ見える) | 許可した場所だけ読める |
| ネットワーク | 設定すれば、宛先の許可リスト + キーの置き換え | 許可リスト + 厳格モード |
| キーの扱い | ダミーの値で VM に入れない(設定が要る) | プロキシ。キーが箱の中に見える可能性(環境変数) |
| 無人運転(止まらないか) | 設定しだい | **厳格モードで止まらない** |
| 公式か | **Pi 公式** | コミュニティ製 |
| 成熟度 | 実験的 | 研究プレビューの部品の上 |
| `sudo` が要る設定 | `/dev/kvm` のグループ(あれば) | **AppArmor の設定(Ubuntu 24.04 以降)** |
| サブエージェント | 子は自動では隔離されない | 拡張自身の `subagent` で隔離(名前の衝突) |
| 検証コマンド(`harness_verify`) | VM の中で動く(イメージの作り込みが要る) | 箱の中で、ふだんどおり動く |

## 4. 私たちのハーネスとの関係(どちらでも共通)
- **Git・GitHub の書き込み(`harness_pr_*`、`harness_worktree`)は、拡張がホストで実行する**ので、どちらの箱の外。箱の中の `bash` は、`git push` も `gh pr merge` も、ガードが拒否する。**トークンを箱の中に置かない**設計と整合する。
- **ガードは残す。** 箱の中でも、作業ディレクトリの中の破壊(`.git` の削除など)や、既定ブランチへの操作は、ガードが止める。
- **私たちのサブエージェントの子プロセスを、箱で包む必要がある。** 方式 A(別プロセス)のままなら、子の起動を `bwrap` などで包むか、子にも同じ拡張を読み込ませる。

## 5. 暫定の見立て
Nix とホストの道具をそのまま使えることと、厳格モードで止まらないことから、**B を先に試す**のが現実的です。ただし、Ubuntu のバージョンと、`sudo` の設定を、先に確認する必要があります。A は、隔離の強さを優先し、Nix をやめて VM の中に道具を入れ直す覚悟があるときの選択です。
