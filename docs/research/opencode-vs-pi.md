# OpenCode のハーネスを改造する案と、Pi でハーネスを作る案の比較

- 日付: 2026-11-13
- 出典: OpenCode の公式ドキュメント(Plugins、Server plugin、Agents、Permissions、Providers)。**私が読んだ範囲**。各ページは要約で返ってきており、読めなかった部分は「確認できず」と書く。Pi は、公式ドキュメント(1.5.2)と、このリポジトリの実装・統合テスト
- 問い(ユーザー): OpenCode Go のサブスクだけを使うなら、Pi ではなく、OpenCode のハーネスを改造するだけでよいのではないか

## 結論
**ユーザーの見立ては、半分正しいです。**
- 「3 つのプロバイダ(Go、Anthropic API、Codex)を使うから、Pi が必要」という理由は、**成り立ちません。** OpenCode も、3 つとも使えます(下記)。
- Go だけなら、OpenCode を改造する案は、十分に現実的で、作る量が少なくて済みます。
- ただし、「**確定した計画を、止まらずに完走させる自律ループ**」と「**決定論的な強制**」を最重視するなら、**Pi のほうが、境界が明確で、確実**です。OpenCode には、**未確認の点が 3 つ**あります(下記)。

## 1. OpenCode で、3 つのプロバイダは使えるか: 使える
| プロバイダ | OpenCode での扱い(公式ドキュメント) |
|---|---|
| OpenCode Go | `/connect` で、OpenCode Go を選ぶ。API キーを入力 |
| Anthropic API | カタログのプロバイダ(キーで利用)。ページには、設定の手順の詳細なし |
| Codex | OpenAI を選び、「Sign in with ChatGPT」(または従来の Codex のサインイン)。使用量はプランから引かれる |

## 2. 比較

| 観点 | OpenCode(公式ドキュメントで確認) | Pi(実装して確認) |
|---|---|---|
| 拡張の形 | プラグイン(TypeScript / JavaScript)。`.opencode/plugins/` や npm・Git | 拡張(TypeScript)。`~/.pi/agent/extensions/` や npm・Git |
| ツール呼び出しの拒否 | `permission.evaluate` フックで `deny`(**許可・確認の判定に対して**。設定済みの拒否はそのまま有効)。`tool.execute.before` は、入力の確認・書き換えで、**中止できるとは書かれていない** | `tool_call` で `{ block: true }`。入力の書き換えも可 |
| システムプロンプトの注入 | `context` フックで、`system`・`messages`・`tools` を、その 1 回の呼び出しだけ変更 | `before_agent_start` で、名前つきのセクションを追加 |
| 出力の加工(秘匿など) | `tool.execute.after` で、結果を書き換え | `tool_result` で、結果を書き換え |
| 最終メッセージの書き換え(完了の 1 行) | **確認できず**(該当するフックが、ドキュメントにない) | `message_end` で、確定したメッセージを置換 |
| 要約(compact)の制御 | `compaction` フックで、要約を差し替え | `session_before_compact` で、要約を差し替え |
| ツール・コマンドの追加 | `ctx.tool.transform`、`ctx.command.transform` | `registerTool`、`registerCommand` |
| **自律ループの継続** | **未確認。** 「セッションが落ち着いた(idle)」ときのフックが、ドキュメントにない。`ctx.session.prompt` で追撃は送れ、`ctx.event.subscribe` でイベントを購読できるが、**イベント名の一覧がない** | `agent_before_settle`(継続を 1 回要求)、`agent_settled`(通知)。リトライや要約のあとの、本当の終わりを区別できる |
| 権限の仕組み | **組み込み**: `allow` / `ask` / `deny`、`shell` のコマンドのパターン(`git push *`)、`external_directory`、エージェントごとの上書き、`policies`(強制の拒否) | 組み込みなし(ガードを自作した) |
| サブエージェント | **組み込み**: 子のセッション、常に背景、**子は自分の権限**を持つ、`steps` の上限、`description` でモデルが選ぶ。`general` は、さらに子を作れない | 組み込みなし(別プロセス方式で自作) |
| エージェントの定義 | Markdown(`mode`・`model`・`permissions`・`steps`・`system`)。**プラグインからは、エージェントを足せない**(変更・選択のみ) | Markdown(`name`・`description`・`tools`・`model`) |
| OS のサンドボックス | **なし**(`shell` は、ホストのユーザーの権限で動く。ドキュメントに明記) | なし(同じ) |
| API の安定性 | V1 と V2 の併存。「V2 の設定では、`tools`・`permission`・`maxSteps` などの従来の項目を使わない」とあり、**移行の途中** | 更新が速く、破壊的な変更もある(1.x でも) |
| 自作の量 | **少ない**(権限、サブエージェント、エージェントが、すでにある) | **多い**(ガード、サブエージェント、ループを作った) |
| Go との関係 | Go の標準のクライアント | 検証済みのクライアント(公式の一覧) |

## 3. OpenCode で、確かめないと分からないこと(3 つ)
1. **自律ループを、どのイベントで継続するか。** idle のイベントの名前が、ドキュメントにない。ここが決まらないと、「完走するまで止まらない」仕組みを、確実に作れない。
2. **最終メッセージの最後の 1 行を、確実に書き換えられるか。** 該当するフックが見つからなかった。
3. **ツールの実行そのものを、フックで中止できるか。** `permission.evaluate` の `deny` で代用できるが、「許可・確認の判定に対して」働く。確認(`ask`)の既定が、無人運転では止まる原因になる。

## 4. どちらにするか
| 優先すること | おすすめ |
|---|---|
| **少ない作業量**、公式の対応、権限とサブエージェントを、すでにある仕組みで使いたい | **OpenCode** を改造する |
| **決定論的な強制と、完走する自律ループ**、境界の明確さ | **Pi**(すでに作ってある) |
| 3 つのプロバイダを使う | どちらでも可(理由にならない) |

私の見立て: **Pi のまま進めるのが無難**です。理由は、(1)重視されている自律ループの境界が、Pi では公式に明確、(2)すでに、ガード・計画・ループ・サブエージェントを、実際の Pi で統合テストまで通している、(3)作ったコードの多くは、**純粋な関数**(シェルの解析、Git・削除・インストール・秘密のガード、計画の状態機械、ループの判断、完了報告、PR のゲート、使用率のパーサー)で、**Pi に依存しない**ため、将来 OpenCode に移るときも、接続部分(`register.ts`)を書き直すだけで、再利用できるからです。

ただし、「Go だけを使い、作る量を減らしたい」が最優先なら、OpenCode は有力です。決めかねるときは、**小さな検証(数時間)**で、上の未確認の 3 点を、実際の OpenCode で確かめるのが確実です。
