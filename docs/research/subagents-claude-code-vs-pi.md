# Claude Code のサブエージェントと、Pi のサブエージェントの違い

- 日付: 2026-11-13
- 出典: Claude Code の[公式ドキュメント(Create custom subagents)](https://code.claude.com/docs/en/sub-agents)(私が読んだ。末尾の約 17,000 文字は未読)、Pi の公式サンプル `examples/extensions/subagent/`(ソースを読んだ)、このリポジトリの実装(統合テストで動作を確認済み)、コミュニティの `pi-subagents` 2 種類(README の説明。ソースは未読)
- 関連: [../subagent-design.md](../subagent-design.md)(方式 A〜C の比較と改造プラン)

## 1. Claude Code のサブエージェントとは
**「専用の指示とツールを持つ、使い捨ての助手」**です。メインの会話とは**別の文脈(コンテキスト)**で作業し、**最後の報告だけ**がメインに返ります。調査のログや、大量のファイルの中身で、メインの会話を埋めないための仕組みです。

- **文脈の分離:** 会話の履歴は見えない。見えるのは、その助手自身のシステムプロンプト、メインが書いた依頼文、`CLAUDE.md`(と git の状態)だけ。
- **定義:** Markdown ファイル(`.claude/agents/*.md`、`~/.claude/agents/*.md`)。先頭の YAML で、`name`・`description`(必須)、`tools`(許可)、`disallowedTools`(拒否)、`model`、`permissionMode`、`maxTurns`、`skills`、`mcpServers`、`hooks`、`memory`、`background`、`isolation: worktree`、`effort` などを指定し、本文がシステムプロンプトになる。
- **呼び出し:** (1) `description` に合うと、Claude が自動で任せる、(2) 「○○のサブエージェントを使って」と頼む、(3) `@` でメンションして必ず使わせる。
- **標準の助手:** Explore(読み取り専用の高速な調査)、Plan(計画のための調査)、general-purpose(探索と変更の両方)など。
- **動かし方:** 前景(終わるまでメインが待つ)と背景(並行して動く)。並列は既定で最大 20。
- **再開:** `SendMessage` で、履歴を保ったまま続きを頼める。会話の記録は別ファイルに残る。
- **入れ子:** 既定で、メインから数えて 3 段まで。
- **権限とフック:** 権限は、メインの設定を引き継ぐ。`settings.json` のフック(`PreToolUse` など)は、サブエージェントのツール呼び出しにも**効く**。
- **返るもの:** 最後の報告だけ。報告に、システムのタグを装った文字列があれば、目印を付ける。
- **制限:** 助手からユーザーへの質問(`AskUserQuestion`)はできない。履歴を引き継がないので、依頼文に必要な情報を入れる必要がある。

## 2. Pi には、もともとサブエージェントはない
Pi は、意図的にサブエージェントを**本体に持たない**設計です(公式: 「サブエージェントや plan mode は付属しない。拡張で作るか、パッケージを入れる」)。そのため、**3 つの入手方法**があります。

| 入手方法 | 何か |
|---|---|
| **公式のサンプル** | `examples/extensions/subagent/`。Claude Code 風の、`.md` に `name`・`description`・`tools`・`model` を書く形式。`pi` を**別のプロセス**として起動して任せる。単発・並列・連鎖。約 1,000 行 |
| **コミュニティのパッケージ** | `nicobailon/pi-subagents`(月 93 万 DL)、`tintinweb/pi-subagents`(「Claude Code 風の Agent ツール」)。前景・背景、並列、worktree 隔離、保存できるワークフロー、進捗画面など、機能が多い。親の Pi の**内部**で子のセッションを動かす |
| **自作(このリポジトリ)** | 公式のサンプルを土台に、ハーネスの要件に合わせて作った(別プロセス方式) |

## 3. 比較: Claude Code / 自作(このリポジトリ) / コミュニティのパッケージ

| 観点 | Claude Code | 自作(このリポジトリ) | コミュニティのパッケージ |
|---|---|---|---|
| 実装の位置 | 本体の機能 | 拡張(自分でコードを持つ) | 拡張(他人のコード) |
| 子の動き方 | 本体が管理する、別の文脈 | **別の OS プロセス**(`pi` の子) | 親のプロセスの内部(前景)/ 常駐の別プロセス(背景) |
| 定義の形式 | `.md` + YAML(項目が多い) | `.md` + YAML(`name`・`description`・`tools`・`model`) | 似た形式 |
| 文脈 | 分離。`CLAUDE.md` と git の状態は見える | 分離。Pi のコンテキストファイル(AGENTS.md など)は、設定しだいで見える | 分離 |
| ツールの制限 | `tools` / `disallowedTools`(本体が強制) | `tools`(`--tools` で、Pi が起動時に強制) | パッケージしだい |
| 権限の確認 | 権限モード。前景の確認は、ユーザーに通る | **確認の画面がない**(子は質問できない)。ガードが、確認が要る操作を拒否 | パッケージしだい |
| ガード・フック | `settings.json` のフックが、子にも効く | 子に**ハーネスの拡張だけ**を読み込ませ、同じガードが子でも効く。`PI_SUBAGENT=1` で子を判別 | **未確認**(内部実行なので、親のフックが子に効くかは要検証) |
| モデル | 役割ごとに `model`(`inherit` もできる) | 全員 `/subagent-model`(既定: DeepSeek V4.1 Flash)。役割に `model` も書ける | 役割ごとの指定ができる |
| 入れ子 | 既定で 3 段まで | **不可**(子は `subagent` ツールを持たない) | パッケージしだい(再帰の防止あり) |
| 並列 | 既定で最大 20 | 1 回に 8 件、同時 4 | あり(多い) |
| 前景・背景 | 両方 | **前景のみ**(終わるまでメインが待つ) | 両方 |
| 再開(続きを頼む) | `SendMessage` で、履歴を保って再開 | **不可**(`--no-session`。使い捨て) | あり(パッケージによる) |
| worktree 隔離 | `isolation: worktree` で自動 | 手動(`harness_worktree` で作り、`cwd` で渡す) | あり(自動) |
| 自動で任せる判断 | `description` と合えば、モデルが判断 | ツールの説明に、役割の一覧を載せ、モデルが判断(同じ考え方) | 同様 |
| 返るもの | 最後の報告だけ(注入の目印あり) | 最後の報告(上限 50KB)+ 使用量・費用の行 | 最後の報告 |
| 表示 | 一覧 | 「⏳ サブエージェント（モデル）で〜を実行中」「✅ 〜が完了」 | 進捗画面(FleetView など) |
| 費用 | メインの上限に合算 | 子の費用を、メインの使用額に合算して表示 | あり |

## 4. 違いの本質
1. **強制のしかた。** Claude Code は、本体が権限モードとフックで、子を縛る。Pi には権限の仕組みがないので、**拡張が、子に「ガードの拡張」を読み込ませる**ことで、同じ縛りを作る。自作は、これを**プロセスの境界と環境変数**で行うため、「commit・push・PR・マージは、メインだけ」を、子のモデルが書き換えられない形で強制できる。
2. **別プロセスか、内部か。** 別プロセスは、**境界が明確**(子だけをサンドボックスで包める、暴走しても親に影響しない)。代わりに、起動が重く、状態の共有や再開が難しい。内部は、軽くて機能を足しやすいが、境界がなく、親のフックが子に効くかが、実装しだい。
3. **機能の量。** Claude Code は、背景・再開・入れ子・自動 worktree・記憶・フックなどが、そろっている。自作は、要件(決定論的な強制、日本語、費用の合算、表示文言)に絞った**最小構成**。

## 5. Claude Code 風に近づけるには(できるか)
**できます。** Pi の拡張の仕組みで、多くを足せます。難しさと、必要かどうかの目安です。

| 足す機能 | 方法 | 難しさ | 必要性 |
|---|---|---|---|
| `disallowedTools`(拒否リスト) | 起動時に、許可リストから引く | 低 | 中 |
| `maxTurns`(ターン数の上限) | 子の起動引数か、JSON イベントを数えて停止 | 低 | 中(暴走防止。すでに時間切れはある) |
| 役割ごとの `effort`(思考の深さ) | `--thinking` を渡す | 低 | 低 |
| 自動の worktree 隔離(`isolation: worktree`) | 子の起動前に `harness_worktree` を呼び、終了後に回収 | 中 | 高(並列に書き込むとき) |
| 再開(`SendMessage` 相当) | `--no-session` をやめ、セッションを保存して `--session` で再開 | 中 | 中 |
| 背景実行 | 子を切り離して起動し、完了を通知で受ける(`agent_settled` の継続と組み合わせる) | 中〜高 | 中 |
| 入れ子(深さの制限つき) | 子に `subagent` ツールを持たせ、深さを環境変数で数える | 中 | 低(再帰の事故が増える) |
| `skills` の事前読み込み、`memory` | 子に、スキルのパスや記憶のファイルを渡す | 中 | 低〜中 |
| `@` メンションで必ず使わせる | `input` イベントで、メンションを検出して指示を足す | 中 | 低 |
| 役割ごとのフック | 子ごとに、読み込む拡張を変える | 中 | 低 |

**おすすめの順序:** 自動の worktree 隔離 → `maxTurns` → 再開 → 背景実行。どれも、今の別プロセス方式の延長で足せます。

## 6. どれを選ぶか(決定記録 009 は保留)
- **要件の中心が「決定論的に止める」ことなら、自作(別プロセス方式)を育てる**のが筋です。サンドボックスで子を包むときも、プロセス単位で扱えます。
- **機能(背景、再開、worktree、進捗画面)を早く揃えたいなら、コミュニティのパッケージを試す**のも手です。ただし、**親のガードが子に効くか、サンドボックスが子を包めるか**を、必ず先に確かめる必要があります(未確認)。
